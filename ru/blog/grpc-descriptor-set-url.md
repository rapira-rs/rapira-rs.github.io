# Загрузка набора дескрипторов gRPC по URL

Rapira читает схему gRPC из набора дескрипторов. Это один бинарный файл, который содержит скомпилированные файлы `.proto` вместе с импортируемыми файлами. Buf называет такой файл образом (image). Ключ `descriptor_set` секции `[grpc]` теперь принимает две формы: локальный путь и URL с протоколом HTTP или HTTPS.

::: info
Для формы с URL нужна версия Rapira новее 0.9.2.
:::

## Для чего Rapira использует набор

Rapira использует набор, чтобы находить сервисы и их методы, преобразовывать сообщения Connect в формате JSON и отвечать на запросы рефлексии. Мастер-процесс загружает набор один раз при запуске, до создания воркеров через fork. Набор, который Rapira не может загрузить, останавливает запуск. Для этого Rapira не нужен исполняемый файл `protoc`.

## Форма с путём

```toml
[grpc]
descriptor_set = "api.binpb"
```

Относительный путь использует каталог `rapira.toml` как базовый. Файл должен быть на хосте или в контейнере до запуска Rapira. Есть три обычных способа поместить его туда:

- Соберите набор в пайплайне приложения и скопируйте его в образ контейнера.
- Смонтируйте набор из тома или ConfigMap. ConfigMap [не может содержать больше 1 МиБ](https://kubernetes.io/docs/concepts/configuration/configmap/#motivation).
- Скачайте набор в [init-контейнере](https://kubernetes.io/docs/concepts/workloads/pods/init-containers/) или в скрипте точки входа.

При первых двух способах Rapira читает локальный файл при запуске и не отправляет запросов. При третьем способе запуску нужен хост файла, как и в форме с URL. Если набор находится в образе, набор и код приложения развёртываются как один артефакт. Но каждому сервису нужен ещё один шаг: этап сборки с `buf` или `protoc` или скрипт, который получает файл.

## Форма с URL

```toml
[grpc]
descriptor_set = "https://schemas.example.com/billing/v42/api.binpb"
```

Значение, которое начинается с `http://` или `https://`, является URL. Мастер-процесс скачивает набор запросом GET при запуске. [Входные данные Buf в формате образа](https://buf.build/docs/reference/inputs/#image-formats) так же принимают удалённое расположение.

С этой формой можно хранить наборы дескрипторов всех сервисов в одном месте. Пайплайн репозитория `.proto` собирает каждый набор один раз:

```sh
buf build proto --as-file-descriptor-set -o api.binpb
```

Затем пайплайн выгружает `api.binpb` на хост, который отвечает на запрос GET. Например, это бакет объектного хранилища, репозиторий артефактов или сервер статических файлов. Каждый экземпляр Rapira указывает этот URL в `rapira.toml`.

Rapira скачивает набор самостоятельно. Образ приложения не содержит набора дескрипторов и шага, который его собирает. Поду не нужны init-контейнер и том для схемы. Одна и та же конфигурация работает в контейнере, на виртуальной машине и на компьютере разработчика.

## Как работает скачивание

- Rapira отправляет запрос GET и следует не более чем 10 перенаправлениям. Статус ответа 400 или выше останавливает запуск.
- HTTPS использует системное хранилище сертификатов. `SSL_CERT_FILE` и `SSL_CERT_DIR` выбирают другое хранилище, например для частного центра сертификации.
- Rapira отправляет часть userinfo из URL (`https://user:password@host/api.binpb`) как учётные данные HTTP Basic. Записи лога показывают URL без userinfo и без строки запроса.
- Скачивание использует прокси, который задаёт `ALL_PROXY`, `HTTPS_PROXY` или `HTTP_PROXY`.
- У соединения, заголовков ответа и тела есть свой предел времени 30 секунд. Наибольший размер набора - 64 МиБ.

## Ограничения формы с URL

Форма с URL переносит одну зависимость из сборки в запуск каждого экземпляра. Прочитайте эти ограничения перед использованием.

- Для запуска нужен хост схемы. Если скачивание не удалось, Rapira завершается с кодом 1. Rapira не повторяет попытку и не хранит локальную копию. Супервизор процессов или оркестратор должен запустить Rapira снова. Работающие экземпляры это не затрагивает, потому что они не скачивают набор повторно.
- Изменённый набор требует перезапуска. Перезагрузка сохраняет загруженный набор. Если вы замените файл по URL, экземпляры с разным временем запуска могут использовать разные наборы. Укажите версию в пути URL и меняйте URL для каждого релиза схемы.
- Rapira не проверяет содержимое. Контрольная сумма и подпись не проверяются. Используйте HTTPS и хост, которому вы доверяете. При `http://` любой хост на сетевом пути может изменить набор.
- Аутентификация простая. Rapira может отправить учётные данные HTTP Basic из части userinfo в URL. Строка запроса URL тоже может содержать учётные данные, как в предварительно подписанном URL. Rapira не может отправить bearer-токен и не может подписать запрос к API облачного хранилища. У предварительно подписанного URL есть срок действия, и запуск после этого срока завершается ошибкой. Учётные данные находятся в `rapira.toml`, поэтому защитите этот файл.
- Формат фиксирован. Тело ответа должно быть бинарным набором. Buf также может читать сжатый образ, например `image.binpb.gz`, а Rapira не может.
- Rapira не использует API реестра схем. Rapira отправляет обычный запрос GET. Экспортируйте набор из реестра и выгрузите его на хост, который отвечает на запрос GET.
- Сгенерированные классы PHP остаются в приложении. Приложение, которое использует сгенерированные классы сообщений, по-прежнему включает их в свой образ при сборке. Форма с URL убирает из образа только набор дескрипторов. Держите классы и набор в одной версии схемы.

## Какую форму выбрать

Используйте путь, если набор поставляется вместе с приложением или если Rapira должна запускаться без доступа к сети. Используйте URL, если много сервисов или экземпляров используют одно расположение схем и это расположение доступно настолько, насколько требуют ваши развёртывания.

Справочное описание приведено в разделе [gRPC](/ru/docs/grpc#descriptor-set-url).
