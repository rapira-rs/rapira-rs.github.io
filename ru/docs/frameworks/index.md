# Интеграция с фреймворками

В режиме Classic приложение на фреймворке работает без изменений. Настройте Rapira для использования существующего входного скрипта.
В режиме Worker процесс PHP остаётся активным между запросами. Архитектура фреймворка определяет, какое состояние приложения может оставаться в памяти.
Эта страница описывает общее поведение. Руководства по фреймворкам описывают только особенности конкретного фреймворка.

::: info Проверено на

- **PHP 8.5.8**, NTS, embed SAPI.
- **Rapira 0.8.0**.
- **Symfony 7.4.15** и **8.1.2**, шаблон приложения **Yii3** 1.4 (yii-runner-http 3.2.1).

Всё, что написано на этой странице, получено запуском этих приложений на Linux с одним процессом воркера. Утверждения о поведении фреймворков опираются на эти прогоны, а ключи конфигурации взяты из справочника [Конфигурация](/ru/docs/configuration) самой Rapira.
:::

## Режимы Classic и Worker

**В режиме Classic используется существующий входной скрипт.** Для каждого HTTP-запроса Rapira запускает новый запрос PHP.
Фреймворк, который работает под php-fpm, также работает в этом режиме. Дополнительная информация находится на странице [Режим Classic](/ru/docs/classic).
К режиму Classic также относятся разделы о статических файлах, TLS и OPcache.

**В режиме Worker процесс остаётся активным.** Скрипт инициализирует приложение и запрашивает работу в цикле.
Состояние приложения остаётся между запросами. Дополнительная информация находится в разделах [Режимы выполнения](/ru/docs/execution-modes) и [Режим Worker](/ru/docs/worker).

Одна кодовая база может использовать оба режима. Оставьте `public/index.php`. Добавьте рядом `worker.php`.
Используйте `--mode` для выбора режима выполнения. Выберите скрипт аргументом `SCRIPT` или параметром `pool.entrypoint`.
Используйте режим Classic, если переход на режим Worker не работает.

## Цикл Worker

Для каждого фреймворка используется одна базовая структура скрипта воркера:

```php
<?php
// worker.php
require __DIR__ . '/vendor/autoload.php';

$app = new App(); // The worker creates this object once and reuses it.

$handler = static function () use ($app): void {
    header('Content-Type: text/plain');
    http_response_code(200);
    echo $app->handle($_SERVER['REQUEST_URI']);
};

while (\Rapira\handle_request($handler)) {
    gc_collect_cycles();
}
```

Скрипт выполняет следующие операции:

- **`require .../vendor/autoload.php`** регистрирует автозагрузчик на всё время работы воркера. Загруженные классы остаются доступными.
- **`$app = new App();`** инициализирует приложение перед циклом. Symfony хранит здесь постоянное ядро.
- Yii3 может хранить постоянный раннер или создавать раннер в обработчике. Каждое руководство содержит необходимую инициализацию и очистку запроса.
- **`$handler = static function () use ($app): void`** определяет обработчик без аргументов. Обработчик читает запрос из суперглобальных переменных.
- Обработчик захватывает другие зависимости с помощью `use`.
- **`header()`, `http_response_code()` и `echo`** формируют ответ как в классическом скрипте. Передача ответа описана в разделе [HTTP](/ru/docs/http).
- **`while (\Rapira\handle_request($handler))`** ожидает запрос. `handle_request()` заполняет суперглобальные переменные, запускает обработчик и завершает запрос.
- Функция возвращает `true` после запроса и `false` при остановке воркера. Вызывайте её только из цикла верхнего уровня.
- Вне режима Worker функция бросает `Rapira\Exception\NotInWorkerModeError`.
- **`gc_collect_cycles();`** выполняется между запросами и собирает циклические ссылки. Эта функция не исправляет утечки памяти.
- Дополнительная информация находится в разделе [Память и перезапуск воркеров](#память-и-перезапуск-воркеров).

Rapira задаёт `SCRIPT_NAME` как `/worker.php`, потому что это входной скрипт.
`DOCUMENT_ROOT` содержит каталог скрипта. `REQUEST_URI` содержит путь клиента.
Symfony и Yii3 правильно маршрутизировали запросы и создавали URL с этими значениями. Созданные URL не содержали `worker.php`.
Перед интеграцией другого фреймворка проверьте, использует ли он `SCRIPT_NAME` вместо `REQUEST_URI`.

## Состояние запроса и резидентное состояние

Всё, что стоит в левой колонке, Rapira собирает заново на каждый запрос, поэтому обычный PHP-код, который это читает, продолжает работать. Всё, что в правой, живёт столько же, сколько сам воркер, и управлять этим должен скрипт воркера.

| Обновляется на каждом запросе | Переживает любой запрос |
| ----------------------------- | ----------------------- |
| `$_GET`, `$_POST`, `$_SERVER`, `$_COOKIE` - заполнены данными этого запроса | Автозагрузчик Composer и все классы, уже загруженные через него |
| `php://input` - сырое тело этого запроса, а рядом `CONTENT_TYPE` и `CONTENT_LENGTH` | Свойства и переменные `static` - они продолжают считать сквозь запросы |
| `$_FILES` и временные файлы загрузок за ним | Объекты, созданные до цикла: контейнер, ядро, ваше приложение |
| Всё, что связано с сессией: `session_start()`, кука на входе, `Set-Cookie` на выходе | Открытые ресурсы: соединения с базой, клиенты кеша, потоки |
| Состояние ответа: код статуса, заголовки, `setcookie()`, буферы вывода | Сам процесс - тот же pid, один резидентный интерпретатор PHP на воркер |
| Shutdown-функции, зарегистрированные **внутри** обработчика | Собственные счётчики воркера: `handled` и `errors` продолжают увеличиваться |
| Таймер `max_execution_time`, взводимый заново на каждый запрос | |

На Linux (и на FreeBSD), где у Zend есть таймер на запрос, таймер `max_execution_time` взводится заново для каждого запроса, а время, которое воркер простоял в ожидании следующего, ему никогда не засчитывается: на счётчике оказывается только сам запрос. На остальных платформах, включая macOS, таймаут на запрос не взводится вообще.

Следующие три особенности относятся к резидентному воркеру.

::: warning Резидентный объект сохраняет состояние между запросами

PHP не вызывает деструктор резидентного объекта в конце запроса. Деструктор выполняется один раз: когда завершается цикл воркера или когда код удаляет последнюю ссылку на объект.

Не используйте деструктор для очистки, которая нужна после каждого запроса. Сбрасывайте состояние запроса внутри обработчика.
:::

::: warning Shutdown-функция, зарегистрированная при инициализации, срабатывает один раз при остановке воркера

Shutdown-функцию, зарегистрированную вне обработчика, PHP выполняет один раз, в конце цикла воркера. Функция, зарегистрированная внутри обработчика, выполняется в конце этого запроса.

Регистрируйте shutdown-функции запроса внутри обработчика. К таким функциям относятся вывод метрик, обработка фатальной ошибки и очистка ресурсов запроса.
:::

::: warning PHP может повторно импортировать `$_ENV` во время запроса

При стандартных настройках ini PHP сбрасывает JIT-флаг для `$_ENV` при каждом запросе.
Первый новый скомпилированный файл, который использует `$_ENV`, заставляет PHP снова создать эту суперглобальную переменную.
Если в `variables_order` нет `E`, PHP не импортирует значения. Поэтому `$_ENV` становится **пустым** без диагностического сообщения.
Это удаляет значения, которые процесс Dotenv записал в `$_ENV` при инициализации.

Результат зависит от времени компиляции файла. Конфигурация, обработанная при инициализации, может использовать значения до очистки `$_ENV`.
Конфигурация, обработанная во время первого запроса, может прочитать пустой `$_ENV`. Это различие может вызвать ошибки только в некоторых средах.

Доступны два решения. Запишите значения в окружение процесса с помощью `putenv()`.
Повторный импорт сохраняет эти значения, и фреймворк может прочитать их через `getenv()`.
В продакшене задайте переменные окружения в unit-файле или контейнере. Не обрабатывайте `.env` во время запросов.
При `variables_order = "GPCS"` оба решения оставляют `$_ENV` пустым. Пример находится в [руководстве по Symfony](/ru/docs/frameworks/symfony).

С этим сталкивается любой рантайм PHP, который держит процесс живым между запросами.
:::

## Обработка ошибок

Тесты подтвердили три типа ошибок с одним воркером:

- **`exit` или `die` внутри обработчика** отправляет текущий статус и вывод. Воркер продолжает принимать запросы.
- Фреймворк может использовать `exit` для ответа о техническом обслуживании без завершения процесса.
- **Непойманное исключение** возвращает `500`. Обработчик ошибок фреймворка может вернуть свою страницу ошибки.
- Без такого обработчика Rapira возвращает пустое тело. Воркер продолжает принимать запросы.
- **Непойманная `Error`** также возвращает `500`, и воркер продолжает работу. PHP записывает сообщение `Uncaught Error`.

Счётчик `errors` увеличивается в двух случаях ошибок. Запрос с `exit` возвращает `200` и увеличивает только `handled`.
Во всех трёх случаях `recycles` и `restarts` остаются равны нулю. Непойманный throwable не останавливает воркер и не изменяет следующий запрос.
Фатальная ошибка класса bailout завершает резидентный скрипт. Воркер снова запускает скрипт и инициализирует приложение.
Это действие увеличивает `recycles`. Страница [Модель процессов](/ru/docs/process-model) описывает вывод этих счётчиков.

## Статические файлы

Статику Rapira отдаёт через [middleware статических файлов](/ru/docs/static-files). Направьте `root` в секции `[http.static]` на каталог `public/` вашего фреймворка, а сам middleware перечислите в `[http]`:

```toml
[http]
middleware = ["static"]

[http.static]
root = "public"
```

Middleware отвечает на запрос только тогда, когда путь ведёт к файлу внутри этого корня. Список `forbid` по умолчанию не выпускает наружу файлы `.php`, поэтому входной скрипт из `public/` файлом не отдаётся никогда. Любой другой URL выполняет входной скрипт - одинаково в режимах Classic и Worker, - а куда именно хотел попасть клиент, приложение узнаёт из `$_SERVER['REQUEST_URI']`. URL каталога тоже выполняет входной скрипт: индексный файл middleware для него не отдаёт.

Отдавать статику по-прежнему может и то, что стоит перед Rapira: сеть доставки контента или обратный прокси. Настройку такого прокси разбирает [Запуск в продакшене](/ru/docs/deployment).

## TLS и прокси

Слушающий сокет Rapira говорит по открытому HTTP, а раздела про TLS в конфигурации нет. Терминируйте TLS на том прокси, который у вас и так работает, и пустите его к Rapira через петлевой интерфейс или Unix-сокет. Проброшенные поля прокси должен писать через `-` и никогда через `_`: оба написания схлопываются в один и тот же ключ `$_SERVER`. Про это преобразование рассказывает раздел [HTTP](/ru/docs/http), а про настройку прокси - [Запуск в продакшене](/ru/docs/deployment).

## Память и перезапуск воркеров

Воркер может создавать приложение внутри обработчика. В этой схеме приложение существует в течение одного запроса.
Она сохраняет меньше состояния, чем постоянное ядро Symfony, но больше, чем режим Classic.
Цикл остаётся в скрипте воркера. Переносите инициализацию из обработчика только после проверки постоянного состояния.
В этой схеме контейнер создаётся после получения запроса.

В этой схеме каждый запрос создаёт граф объектов. Циклические ссылки могут сохранять старые графы до запуска сборщика циклов.
Использование памяти растёт несколько запросов и уменьшается после освобождения нескольких графов. Такое циклическое использование не обязательно является утечкой.
Однако максимальное использование памяти может значительно превышать использование одного запроса.

Тесты показали, что `gc_collect_cycles()` в цикле или обработчике не устраняет это поведение.
Более поздняя инициализация может сохранять ссылки на старые графы. Сборщик не может освободить граф, пока другой объект ссылается на него.
Установите `memory_limit` выше измеренного максимума. Также установите лимит замены воркера:

```toml
[pool]
max_requests = 100
```

Мастер заменяет воркер после достижения лимита запросов. Rapira немного изменяет лимит, чтобы предотвратить одновременную замену.
Тесты отправили сотни запросов во время нескольких замен. Память возвращалась к исходному уровню, и каждый запрос возвращал `200`.
Эта настройка устанавливает предсказуемый предел использования памяти.

Резидентные схемы - ядро Symfony, контейнер Yii3 за `StateResetter` - на этом фоне ровные: на тех же прогонах память держалась на одном уровне. Перезапуск воркеров держите включённым и для них, как подстраховку. Сам ключ описан в [Конфигурации](/ru/docs/configuration), а что перезапуск делает с пулом, рассказывает [Модель процессов](/ru/docs/process-model).

## OPcache и изменившийся код

Rapira запускает PHP один раз в мастер-процессе до создания воркеров. OPcache создаёт один сегмент разделяемой памяти.
Каждый воркер наследует это отображение. Скомпилированные скрипты остаются кешированными между запросами и воркерами в обоих режимах.

В продакшене `opcache.validate_timestamps = 0` убирает `stat` по каждому файлу на каждом запросе. При этой настройке кеш больше ничем не инвалидируется. Сегмент принадлежит мастер-процессу и переживает любое поколение воркеров. Поэтому плавная перезагрузка продолжит отдавать старые опкоды, и на деплое нужен полный перезапуск. Весь порядок действий расписан в разделе [Запуск в продакшене](/ru/docs/deployment).

Во время разработки постоянное приложение не перечитывает код инициализации. Это поведение не зависит от OPcache.
Перезапускайте сервер после изменения скрипта воркера или инициализированных сервисов. Нажмите Ctrl-C, затем снова запустите `rapira serve`.

## Руководства по фреймворкам

- **[Symfony](/ru/docs/frameworks/symfony)** - ядро поднимается один раз и остаётся резидентным, а собственный `services_resetter` фреймворка между запросами возвращает сервисы с состоянием в то положение, в каком их застал. Один и тот же файл воркера, байт в байт, подходит и для 7.4, и для 8.1.
- **[Laravel](/ru/docs/frameworks/laravel)** - режим Classic: штатный `public/index.php` работает без изменений. Режим Worker для Laravel в разработке: резидентному приложению на Laravel нужен тот сброс состояния, который реализует Octane, а драйвера Octane у Rapira пока нет.
- **[Yii3](/ru/docs/frameworks/yii3)** - `StateResetter` сбрасывает постоянный контейнер после каждого запроса. В качестве альтернативы воркер может создавать новый раннер для каждого запроса.

Другие фреймворки могут использовать тот же базовый скрипт. Используйте режим Worker только для приложения, которое обрабатывает несколько запросов в одном процессе.
Сначала создавайте приложение внутри обработчика. Эта схема не требует поддержки постоянных процессов фреймворком.
После проверки сохраняйте приложение и сбрасывайте состояние запроса. Используйте [режим Classic](/ru/docs/classic), если обе схемы Worker не работают.
