# Интеграция с фреймворками

В режиме Classic приложение на фреймворке работает без изменений. Настройте Rapira для использования существующего входного скрипта. В режиме Worker процесс PHP остаётся активным между запросами. Архитектура фреймворка определяет, какое состояние приложения может оставаться в памяти. Эта страница описывает общее поведение. Руководства по фреймворкам описывают только особенности конкретного фреймворка.

::: info Проверено на

- **PHP 8.5.8**, NTS, embed SAPI.
- **Rapira 0.8.0**.
- **Symfony 7.4.15** и **8.1.2**, шаблон приложения **Yii3** 1.4 (yii-runner-http 3.2.1).

Тесты запускали эти приложения в Linux с одним процессом воркера. Утверждения о фреймворках на этой странице основаны на этих тестах. Параметры Rapira описаны в разделе [Конфигурация](/ru/docs/configuration).
:::

## Режимы Classic и Worker

**В режиме Classic используется существующий входной скрипт.** Для каждого HTTP-запроса Rapira запускает новый запрос PHP. Фреймворк, который работает под php-fpm, также работает в этом режиме. Дополнительная информация находится на странице [Режим Classic](/ru/docs/classic). Только приведённые ниже разделы о статических файлах, TLS и OPcache относятся к режиму Classic.

**В режиме Worker процесс остаётся активным.** Скрипт инициализирует приложение и запрашивает работу в цикле. Состояние приложения остаётся между запросами. Дополнительная информация находится в разделах [Режимы выполнения](/ru/docs/execution-modes) и [Режим Worker](/ru/docs/worker).

Одна кодовая база может использовать оба режима. Оставьте `public/index.php`. Добавьте `worker.php` в корневой каталог проекта. Используйте `--mode` для выбора режима выполнения. Выберите скрипт аргументом `SCRIPT` или параметром `pool.entrypoint`. Используйте режим Classic, если переход на режим Worker не работает.

## Цикл Worker

Для каждого фреймворка используется одна базовая структура скрипта воркера:

```php
<?php
// worker.php
require __DIR__ . '/vendor/autoload.php';

$app = new App(); // The worker creates this object once and reuses it.

$handler = static function () use ($app): void {
    header('Content-Type: text/plain');
    http_response_code(200);
    echo $app->handle($_SERVER['REQUEST_URI']);
};

while (\Rapira\handle_request($handler)) {
    gc_collect_cycles();
}
```

Скрипт выполняет следующие операции:

- **`require .../vendor/autoload.php`** регистрирует автозагрузчик до перезапуска скрипта воркера. Загруженные классы остаются доступными.
- **`$app = new App();`** инициализирует приложение перед циклом. Symfony хранит здесь постоянное ядро.
- Yii3 может хранить постоянный раннер или создавать раннер в обработчике. Каждое руководство содержит необходимую инициализацию и очистку запроса.
- **`$handler = static function () use ($app): void`** определяет обработчик без аргументов. Обработчик читает запрос из суперглобальных переменных.
- Обработчик захватывает другие зависимости с помощью `use`.
- **`header()`, `http_response_code()` и `echo`** формируют ответ как в классическом скрипте. Передача ответа описана в разделе [HTTP](/ru/docs/http).
- **`while (\Rapira\handle_request($handler))`** ожидает запрос. `handle_request()` заполняет суперглобальные переменные, запускает обработчик и завершает запрос.
- Функция возвращает `true` после запроса и `false` при остановке воркера. Вызывайте её только из цикла верхнего уровня.
- Вне режима Worker функция бросает `Rapira\Exception\NotInWorkerModeError`.
- **`gc_collect_cycles();`** выполняется между запросами и собирает циклические ссылки. Эта функция не исправляет утечки памяти.
- Дополнительная информация находится в разделе [Память и перезапуск воркеров](#память-и-перезапуск-воркеров).

Rapira задаёт `SCRIPT_NAME` как `/worker.php`, потому что это входной скрипт. `DOCUMENT_ROOT` содержит каталог скрипта. `REQUEST_URI` содержит путь клиента. Symfony и Yii3 правильно маршрутизировали запросы и создавали URL с этими значениями. Созданные URL не содержали `worker.php`. Перед интеграцией другого фреймворка проверьте, использует ли он `SCRIPT_NAME` вместо `REQUEST_URI`.

## Состояние запроса и резидентное состояние

Rapira пересоздаёт всё в левой колонке для каждого запроса. Обычный код PHP может читать эти значения. Всё в правой колонке сохраняется между запросами. Скрипт воркера должен управлять этим состоянием.

| Создаётся заново для каждого запроса | Сохраняется между запросами |
| ------------------------------------ | ----------------------------- |
| `$_GET`, `$_POST`, `$_SERVER`, `$_COOKIE`: Rapira заполняет их данными запроса | Автозагрузчик Composer и каждый загруженный им класс |
| `php://input`: исходное тело запроса, `CONTENT_TYPE` и `CONTENT_LENGTH` | Свойства и переменные `static`, которые сохраняют значения между запросами |
| `$_FILES` и загруженные временные файлы | Объекты, созданные до цикла, например контейнер, ядро и приложение |
| Данные сессии: `session_start()`, cookie запроса и поле ответа `Set-Cookie` | Открытые ресурсы: соединения с базой данных, клиенты кеша, потоки |
| Состояние ответа: код статуса, заголовки, `setcookie()` и буферы вывода | Процесс: один pid и один резидентный интерпретатор PHP для каждого воркера |
| Shutdown-функции, зарегистрированные **внутри** обработчика | Счётчики воркера: `handled` и `errors` продолжают увеличиваться |
| Таймер `max_execution_time`, который перезапускается для каждого запроса | `$_ENV`, включая значения, загруженные до цикла |

В Linux и FreeBSD Zend запускает новый таймер `max_execution_time` для каждого запроса. Время ожидания воркера не входит в этот лимит. В других системах, включая macOS, PHP не запускает таймер запроса.

Следующие три особенности относятся к резидентному воркеру.

::: warning Резидентный объект сохраняет состояние между запросами

PHP не вызывает деструктор резидентного объекта в конце запроса. Деструктор выполняется один раз: когда завершается цикл воркера или когда код удаляет последнюю ссылку на объект.

Не используйте деструктор для очистки, которая нужна после каждого запроса. Сбрасывайте состояние запроса внутри обработчика.
:::

::: warning Shutdown-функция, зарегистрированная при инициализации, выполняется один раз в конце цикла воркера

Shutdown-функцию, зарегистрированную вне обработчика, PHP выполняет один раз, в конце цикла воркера. Функция, зарегистрированная внутри обработчика, выполняется в конце этого запроса.

Регистрируйте shutdown-функции запроса внутри обработчика. К таким функциям относятся вывод метрик, обработка фатальной ошибки и очистка ресурсов запроса.
:::

::: warning `$_ENV` сохраняется между запросами

Rapira не пересоздаёт `$_ENV` для каждого запроса. Значения, записанные кодом до цикла, доступны до повторного запуска скрипта воркера. Считайте `$_ENV` резидентным состоянием приложения. Загружайте конфигурацию окружения до цикла. Не храните в `$_ENV` данные запроса.

Rapira сохраняет значения в `$_ENV` без `putenv()`. Используйте `putenv()`, когда коду нужны свойства окружения процесса, например `getenv()` или наследование дочерним процессом. В продакшене задавайте переменные окружения в unit-файле, контейнере или оркестраторе.
:::

## Обработка ошибок

Тесты подтвердили три типа ошибок с одним воркером:

- **`exit` или `die` внутри обработчика** отправляет текущий статус и вывод. Воркер продолжает принимать запросы.
- Фреймворк может использовать `exit` для ответа о техническом обслуживании без завершения процесса.
- **Непойманное исключение** возвращает `500`. Обработчик ошибок фреймворка может вернуть свою страницу ошибки.
- Без такого обработчика Rapira возвращает пустое тело. Воркер продолжает принимать запросы.
- **Непойманная `Error`** также возвращает `500`, и воркер продолжает работу. PHP записывает сообщение `Uncaught Error`.

Счётчик `errors` увеличивается в двух случаях ошибок. Запрос с `exit` возвращает `200` и увеличивает только `handled`. Во всех трёх случаях `recycles` и `restarts` остаются равны нулю. Непойманный throwable не останавливает воркер и не изменяет следующий запрос. Фатальная ошибка класса bailout завершает резидентный скрипт. Воркер снова запускает скрипт и инициализирует приложение. Это действие увеличивает `recycles`. Страница [Модель процессов](/ru/docs/process-model) описывает вывод этих счётчиков.

## Статические файлы

Rapira обслуживает статические ресурсы через [middleware статических файлов](/ru/docs/static-files). Задайте для `[http.static].root` каталог `public/` фреймворка. Добавьте middleware в секцию `[http]`:

```toml
[http]
middleware = ["static"]

[http.static]
root = "public"
```

Middleware возвращает ответ, только если путь соответствует файлу в корневом каталоге. Список `forbid` по умолчанию запрещает доступ к файлам `.php`. Поэтому middleware не обслуживает входной скрипт как файл. Для других URL входной скрипт выполняется в режимах Classic и Worker. `$_SERVER['REQUEST_URI']` содержит путь клиента. Для URL каталогов также выполняется входной скрипт, потому что middleware не обслуживает индексные файлы.

Статические ресурсы также может обслуживать CDN или обратный прокси. Конфигурация обратного прокси описана в разделе [Запуск в продакшене](/ru/docs/deployment).

## TLS и прокси

Rapira принимает открытый HTTP и не предоставляет настройки TLS. Завершайте TLS на прокси. Подключите прокси через петлевой интерфейс или Unix-сокет. Используйте дефисы вместо подчёркиваний в именах перенаправленных полей. Оба символа могут соответствовать одному ключу `$_SERVER`. Дополнительная информация находится в разделах [HTTP](/ru/docs/http) и [Запуск в продакшене](/ru/docs/deployment).

## Память и перезапуск воркеров

Воркер может создавать приложение внутри обработчика. В этой схеме приложение существует в течение одного запроса. Она сохраняет меньше состояния, чем постоянное ядро Symfony, но больше, чем режим Classic. Цикл остаётся в скрипте воркера. Переносите инициализацию из обработчика только после проверки постоянного состояния. В этой схеме контейнер создаётся после получения запроса.

В этой схеме каждый запрос создаёт граф объектов. Циклические ссылки могут сохранять старые графы до запуска сборщика циклов. Использование памяти растёт несколько запросов и уменьшается после освобождения нескольких графов. Такое циклическое использование не обязательно является утечкой. Однако максимальное использование памяти может значительно превышать использование одного запроса.

Тесты показали, что `gc_collect_cycles()` в цикле или обработчике не устраняет это поведение. Более поздняя инициализация может сохранять ссылки на старые графы. Сборщик не может освободить граф, пока другой объект ссылается на него. Установите `memory_limit` выше измеренного максимума. Также установите лимит замены воркера:

```toml
[pool]
max_requests = 100
```

Мастер заменяет воркер после достижения лимита запросов. Rapira немного изменяет лимит, чтобы предотвратить одновременную замену. Тесты отправили сотни запросов во время нескольких замен. Память возвращалась к исходному уровню, и каждый запрос возвращал `200`. Эта настройка устанавливает предсказуемый предел использования памяти.

Постоянные приложения Symfony и Yii3 показывали стабильное использование памяти в тех же тестах. Оставьте замену воркеров включённой для ограничения неожиданного роста памяти. Дополнительная информация находится в разделах [Конфигурация](/ru/docs/configuration) и [Модель процессов](/ru/docs/process-model).

## OPcache и изменившийся код

Rapira запускает PHP один раз в мастер-процессе до создания воркеров. OPcache создаёт один сегмент разделяемой памяти. Каждый воркер наследует это отображение. Скомпилированные скрипты остаются кешированными между запросами и воркерами в обоих режимах.

В продакшене `opcache.validate_timestamps = 0` отключает проверку файлов для каждого запроса. Эта настройка запрещает автоматическую инвалидацию кеша. Сегмент OPcache принадлежит мастер-процессу и сохраняется при замене воркеров. Поэтому после развёртывания требуется полный перезапуск. Последовательность описана в разделе [Запуск в продакшене](/ru/docs/deployment).

Во время разработки постоянное приложение не перечитывает код инициализации. Это поведение не зависит от OPcache. Перезапускайте сервер после изменения скрипта воркера или инициализированных сервисов. Нажмите Ctrl-C, затем снова запустите `rapira serve`.

## Руководства по фреймворкам

- **[Symfony](/ru/docs/frameworks/symfony):** ядро инициализируется один раз и остаётся в памяти. `services_resetter` сбрасывает сервисы с состоянием между запросами.
- Один файл воркера поддерживает Symfony 7.4 и 8.1.
- **[Laravel](/ru/docs/frameworks/laravel):** режим Classic запускает стандартный `public/index.php` без изменений.
- Режим Worker для Laravel находится в разработке. Rapira пока не предоставляет требуемый драйвер Octane.
- **[Yii3](/ru/docs/frameworks/yii3):** `StateResetter` сбрасывает постоянный контейнер после каждого запроса.
- Также воркер может создавать новый раннер для каждого запроса.

Другие фреймворки могут использовать тот же базовый скрипт. Используйте режим Worker только для приложения, которое обрабатывает несколько запросов в одном процессе. Сначала создайте приложение внутри обработчика. Эта схема не требует поддержки постоянных процессов фреймворком. Проверьте приложение в этой схеме. Затем сохраняйте приложение между запросами. Сбрасывайте состояние запроса после каждого запроса. Используйте [режим Classic](/ru/docs/classic), если ни одна схема Worker не работает правильно.
