# Laravel

Rapira запускает Laravel в режиме Classic со штатным входным скриптом `public/index.php`. Скрипт выполняется с нуля на каждый запрос, как под php-fpm. Менять в приложении ничего не нужно. Режим Worker для Laravel находится в разработке — о его текущем состоянии рассказывает раздел [Режим Worker](#режим-worker) ниже.

::: info Проверено на
- **PHP 8.5.8** — NTS, embed SAPI
- **Rapira 0.8.0**
- Базовое приложение **laravel/laravel** с **laravel/framework v13.23.0**

Тесты использовали базовое приложение `laravel/laravel` с двумя дополнительными маршрутами. Rapira запускала приложение в режиме Classic с одним рабочим процессом. Тесты проверяли маршрутизацию, сессии, загрузку файлов, запросы JSON и формы. Они также проверяли кеши конфигурации и маршрутов, ответы с ошибками и 50 последовательных запросов.
:::

## Требования

Вам понадобится установленная Rapira — об этом рассказывает [Установка](/ru/docs/intro/installation) — и приложение на Laravel, которое у вас уже запускается. Ещё на машине нужен обычный PHP CLI: через него запускаются Composer и `artisan`. Rapira поставляет PHP библиотекой (`libphp`), а не командой `php`, поэтому эти шаги выполняются на вашем системном PHP, который Rapira не использует и не трогает.

Перед первым запуском проверьте расширения для работы с базой данных: базовое приложение `laravel/laravel` по умолчанию использует SQLite. Оно также хранит в SQLite сессии, кеш и очередь, поэтому ему нужен `pdo_sqlite`. В PHP из релизов Rapira он есть: PDO, `pdo_sqlite` и `sqlite3` входят в набор расширений релизной сборки, который перечислен на странице [Установка](/ru/docs/intro/installation). Если вы запускаете Rapira с PHP собственной сборки, проследите, чтобы эти расширения попали в строку configure — через это проводит [Сборка из исходников](/ru/docs/intro/build-from-source), — либо вместо этого переключите Laravel на файловые и синхронные драйверы: `SESSION_DRIVER=file`, `CACHE_STORE=file`, `QUEUE_CONNECTION=sync`. Именно на этой комбинации проверялось всё, что написано на этой странице.

## Как это запустить

Режим Classic включается явно, поэтому команда прямо его называет:

::: code-group

```bash [CLI]
rapira serve --mode classic public/index.php
```

```toml [rapira.toml]
[pool]
entrypoint = "public/index.php"
mode = "classic"
processes = 4

[http]
listen = "127.0.0.1:8000"
```

:::

С файлом конфигурации команда выглядит как `rapira serve --config rapira.toml`, а относительный `entrypoint` отсчитывается от каталога самого файла. Полный список ключей со значениями по умолчанию собран в [Конфигурации](/ru/docs/configuration).

Rapira выполняет входной скрипт с нуля на каждый запрос, поэтому жизненный цикл фреймворка ровно такой же, как под php-fpm: резидентного состояния нет, сбрасывать между запросами нечего. Прогретым остаётся OPcache: PHP стартует один раз в мастер-процессе, ещё до того как форкнется первый воркер, поэтому все воркеры пользуются общим кешем скомпилированных скриптов — и для вашего кода, и для дерева `vendor/`. Как это устроено, разбирает [Режим Classic](/ru/docs/classic).

Для продакшена сначала соберите кеши фреймворка. Обе команды проверены в режиме Classic: один и тот же набор проверок проходил одинаково и с кешем, и без него.

```bash
php artisan config:cache
php artisan route:cache
```

## Маршрутизация и URL

Rapira не сопоставляет URL с PHP-скриптами: каждый запрос выполняет входной скрипт, а путь для маршрутизации Laravel берёт из `$_SERVER['REQUEST_URI']`. Включённый [middleware статических файлов](/ru/docs/static-files) отвечает на те запросы, которые может закрыть файлом, а все остальные по-прежнему выполняют входной скрипт. Маршрутизация, собственная страница 404 Laravel для несовпавших путей и генерация адресов через `url()` — всё это проверено: получаются аккуратные абсолютные адреса без `index.php` внутри, причём ни подменять `$_SERVER`, ни править настройки маршрутов и URL для этого не нужно.

Базовое приложение содержит маршрут проверки состояния `/up`, который отвечает `200`. Балансировщик или контейнер может использовать этот маршрут для проверки состояния. Rapira отдаёт статические файлы приложения через [middleware статических файлов](/ru/docs/static-files). Включают его сразу двумя половинами: `"static"` в списке `http.middleware` и `root` в секции `[http.static]`, указывающий на каталог `public/` приложения. Если есть только одна половина, Rapira отказывается стартовать. Отдавать статику с прокси или из сети доставки контента перед сервером по-прежнему можно. Rapira слушает открытый HTTP и оставляет `$_SERVER['HTTPS']` пустым независимо от `X-Forwarded-Proto`, поэтому, если [TLS завершается на прокси](/ru/docs/deployment), настройте в Laravel [доверенные прокси](https://laravel.com/docs/requests#configuring-trusted-proxies): без этого `url()` будет выдавать ссылки на `http://`.

## Сессии, CSRF и формы

Сессии проверены на файловом драйвере: кука сессии уходит клиенту, возвращается со следующим запросом, и у каждого клиента своя сессия. CSRF не требует настройки: токен лежит в сессии, а каждый запрос получает ту же семантику свежего процесса, что и под php-fpm. Отправка форм, тела запросов в JSON и загрузка файлов — всё это проверено на той же конфигурации. Когда маршрут бросает исключение, обработчик исключений Laravel рисует свою обычную `500`, а на следующий запрос это никак не влияет.

## Режим Worker

Режим Worker для Laravel находится в разработке и пока не поддерживается — запускайте Laravel в режиме Classic. Сроков появления поддержки пока нет.

Причина — в жизненном цикле фреймворка. Контейнер Laravel не рассчитан на то, чтобы своими силами пережить второй запрос: по ходу запроса разрешаются привязки, синглтоны захватывают текущий запрос, наполняется собственная статика фреймворка, и всё это нужно размотать обратно до прихода следующего запроса. Этим размотыванием и занимается [Octane](https://laravel.com/docs/octane) (`laravel/octane`) — собственный пакет Laravel для долгоживущих серверов. Octane работает только на тех серверах, для которых у него есть драйвер, а драйвера Octane у Rapira пока нет.

Дело не в самом режиме: [Symfony](/ru/docs/frameworks/symfony) и [Yii3](/ru/docs/frameworks/yii3) держат свои приложения резидентными в том же [режиме Worker](/ru/docs/worker). Не хватает специфичной для Laravel работы с состоянием между запросами.

Свой скрипт воркера для Laravel написать можно, но держать приложение резидентным — значит руками повторять то, что Octane делает с состоянием: разматывать приходится состояние, размазанное по контейнеру, разрешённым синглтонам, стеку запроса, сессии и аутентификации, а ещё по собственной статике фреймворка, и один пропущенный пункт оборачивается устаревшим объектом запроса или сессией одного пользователя, видимой другому.
