# Symfony

Symfony поддерживает постоянный воркер. Приложение инициализирует ядро, передаёт ему `Request` и получает `Response`.
Rapira инициализирует ядро один раз для каждого воркера. Затем каждый запрос вызывает `handle()` в инициализированном контейнере.
Код приложения не изменяется. Скрипт воркера заменяет `public/index.php`.
Эта страница описывает этот файл, сброс состояния запроса и значения `.env`.

::: info Проверено на
- **PHP 8.5.8** - NTS, embed SAPI
- **Rapira 0.8.0**
- **Symfony 7.4** (`symfony/framework-bundle` v7.4.15) - полный набор проверок в `dev` и в `prod`
- **Symfony 8.1** (`symfony/framework-bundle` v8.1.2) - полный набор проверок в `dev`

Оба приложения - обычный `symfony/skeleton` под одним процессом воркера, и оба работали с **одним и тем же `worker.php`**: байт в байт, без единой ветки под версию. В набор входят маршрутизация, 404, строки запроса, сгенерированные URL, отправка формы, тело в JSON, сессии, живущие между запросами, загрузка файла, непойманное исключение и 200 запросов подряд.
:::

## Поведение в режиме Worker

Ядро инициализируется вне цикла и остаётся до завершения воркера. Автозагрузчик, контейнер, маршрутизатор, диспетчер событий и соединения инициализируются один раз.
Дополнительная информация находится в разделах [Режим Worker](/ru/docs/worker) и [Режимы выполнения](/ru/docs/execution-modes).

На каждом запросе обработчик делает четыре вещи и прибирается за собой:

1. `Request::createFromGlobals()` - Rapira заново заполняет `$_GET`, `$_POST`, `$_SERVER`, `$_COOKIE` и `$_FILES` перед каждым вызовом вашего обработчика, поэтому обычный конструктор Symfony читает ровно то же самое, что читал бы под php-fpm.
2. `$kernel->handle($request)` - маршрутизация, контроллер, ответ: всё без изменений.
3. `$response->send()` - вывод становится HTTP-ответом (как он упаковывается на выходе, разбирает раздел [HTTP](/ru/docs/http)).
4. `$kernel->terminate($request, $response)` - отрабатывают слушатели, которым положено сработать после ответа, как и всегда.

После этого обработчик сбрасывает сервисы с состоянием через `services_resetter` из контейнера - это тот же самый сброс, который Symfony выполняет между сообщениями Messenger, и именно им долгоживущее ядро избавляется от накопленного за запрос.

Сессии работают как обычные сессии PHP, ровно так же, как под php-fpm: `session_start()` на каждом запросе, кука уходит вместе с ответом, а данные читаются на следующем запросе. Изоляция между клиентами проверена: второй клиент с чистым набором кук получает собственную сессию.

Одно ядро живёт в одном процессе воркера, а воркеры - это отдельные процессы операционной системы, и в пользовательском коде между ними не разделяется ничего. Сколько их и кто за ними присматривает, рассказывает [Модель процессов](/ru/docs/process-model).

## Требования

Установите [Rapira](/ru/docs/intro/installation) и создайте или выберите приложение Symfony. Поместите скрипт воркера рядом с `composer.json`.
Установите PHP CLI для Composer и `bin/console`. Rapira поставляет PHP как библиотеку, а не как команду `php`.
Composer и `bin/console` используют системный PHP CLI. Rapira не использует и не изменяет этот CLI.

Два расширения всё же важны: файл `composer.json` базового приложения требует `ext-ctype` и `ext-iconv`. Он также объявляет `replace` для соответствующих полифилов. Поэтому PHP должен содержать настоящие расширения, а не заглушки. Нужны они обеим сборкам PHP, включая системный CLI: без них `composer create-project` и `composer install` не пройдут проверку платформы ещё до того, как до Rapira вообще дойдёт дело. В PHP, который едет в каждом релизе Rapira, есть оба: `ctype` и `iconv` стоят в строке конфигурации сборки, а полный список расширений собран на странице [Установка](/ru/docs/intro/installation). Если вы собираете Rapira со своим PHP, оставьте оба включёнными - где задаётся этот список, показывает [Сборка из исходников](/ru/docs/intro/build-from-source).

Скрипт воркера ниже также использует `symfony/dotenv`, который входит в базовое приложение. Если у вас на деплое выставлены настоящие переменные окружения и никакого `.env` нет вовсе, выбросьте эту строку, а вместе с ней и сам компонент. Через `symfony/runtime` воркер не проходит - `.env` он поднимает и ядро создаёт сам, - но пакет оставьте установленным, потому что `bin/console` и `public/index.php` по-прежнему им пользуются.

## Скрипт воркера

Положите это в корень проекта под именем `worker.php`. Это тот самый скрипт, что проверялся на обеих мажорных версиях, обновлённый под нынешний API воркера:

```php
<?php

declare(strict_types=1);

use App\Kernel;
use Symfony\Component\Dotenv\Dotenv;
use Symfony\Component\HttpFoundation\Request;

require __DIR__ . '/vendor/autoload.php';

// public/index.php uses symfony/runtime for this operation.
// The worker performs it once before the request loop.
(new Dotenv())->usePutenv()->bootEnv(__DIR__ . '/.env');

$kernel = new Kernel($_SERVER['APP_ENV'], (bool) $_SERVER['APP_DEBUG']);
$kernel->boot();
$container = $kernel->getContainer();

$handler = static function () use ($kernel, $container): void {
    $request = Request::createFromGlobals();

    try {
        $response = $kernel->handle($request);
        $response->send();
        $kernel->terminate($request, $response);
    } finally {
        // Symfony uses the same reset between Messenger messages.
        // Each service with the kernel.reset tag removes request state.
        // The finally block also resets state when send() or terminate() throws.
        if ($container->has('services_resetter')) {
            $container->get('services_resetter')->reset();
        }
    }
};

while (\Rapira\handle_request($handler)) {
    gc_collect_cycles();
}
```

Большая часть здесь - обычный бутстрап Symfony. Специфичны для этой схемы четыре строки:

**`(new Dotenv())->usePutenv()->bootEnv(...)`.** Стандартный `public/index.php` передаёт эту операцию `symfony/runtime`.
Воркер читает `.env` один раз перед созданием ядра. `usePutenv()` сохраняет эти значения, если PHP пересоздаёт `$_ENV` во время запроса.
Дополнительная информация находится в разделе [`$_ENV` и `variables_order`](#env-и-variables-order).

**Ядро инициализируется перед циклом.** `new Kernel(...)`, `boot()` и `getContainer()` выполняются при инициализации воркера.
Поэтому ядро читает `$_SERVER['APP_ENV']` до возможного удаления значений Dotenv. Каждый запрос использует один контейнер.

**Проверка `$container->has('services_resetter')` перед `get()`.** Идентификатор `services_resetter` публичен в обеих поддерживаемых версиях.
Класс реализации использует разные пространства имён в версиях 7.4 и 8.1. Идентификатор сервиса устраняет условие для версии.
Проверка `has()` предотвращает ошибку, если контейнер не определяет сервис.

**Цикл и `gc_collect_cycles()`.** `\Rapira\handle_request()` блокируется, пока не придёт запрос, выполняет ваш обработчик и возвращает `true`. Когда воркер уходит на мягкое завершение, она возвращает `false`, и на этом цикл заканчивается. Сборка циклов один раз за итерацию удерживает эту работу между запросами, а не посреди одного из них. Полный контракт описан в разделе [Режим Worker](/ru/docs/worker).

Если `services_resetter` недостаточно, используйте `$container->reset()` или `$kernel->reboot(null)`. Первый вариант удаляет все созданные сервисы.
Второй вариант удаляет контейнер и создаёт новый.
После `$kernel->reboot(null)` получите новый контейнер через `$kernel->getContainer()`. Обработчик не должен использовать старый контейнер.
Оба варианта удаляют кешированное состояние приложения. Используйте их для поиска утечки, а не как стандартную настройку.

## `$_ENV` и `variables_order`

::: warning
Проверенное базовое приложение использовало `bootEnv()` без `usePutenv()`.
С `variables_order = "GPCS"` и `auto_globals_jit = On` каждый запрос в `prod` возвращал **500**.
Ошибка возникала, когда `RequestContext` читал `DEFAULT_URI` во время запроса.
Исключение: `EnvNotFoundException: Environment variable not found: "DEFAULT_URI"`. То же приложение в `dev` не завершалось с ошибкой.
:::

Причина находится в PHP. С `variables_order = "GPCS"` и `auto_globals_jit = On` PHP сбрасывает JIT-флаг `$_ENV` для каждого запроса.
Первый скомпилированный файл, использующий `$_ENV`, вызывает `php_auto_globals_create_env`. Эта функция снова импортирует `$_ENV` из окружения процесса.
Операция удаляет значения, добавленные `Dotenv->bootEnv()` при инициализации. Тесты наблюдали очистку `$_ENV` во время запроса.

В `prod` первый запрос компилирует контейнер и файлы сервисов. PHP очищает `$_ENV` до обработки `%env(DEFAULT_URI)%` в `RequestContext`.
В `dev` контейнер обрабатывает и кеширует переменные окружения во время `$kernel->boot()`. PHP очищает `$_ENV` после этой операции.
Сброс происходит в обеих средах, но только `prod` использует очищенное значение.

Используйте этот вызов:

```php
(new Dotenv())->usePutenv()->bootEnv(__DIR__ . '/.env');
```

`usePutenv()` записывает значения Dotenv в окружение процесса. Последующий импорт читает эти значения.
Symfony `EnvVarProcessor` также может прочитать их через `getenv()`.
Rapira запускает один интерпретатор NTS PHP в каждом процессе. Поэтому параллельные потоки PHP не вызывают `putenv()`.

В продакшене задайте переменные окружения через systemd, контейнер или оркестратор.
Используйте `.env` только при разработке. И `usePutenv()`, и среда развёртывания записывают значения в окружение процесса.
Поэтому последующий импорт сохраняет значения.

Это поведение относится к каждому постоянному PHP-рантайму, который читает `$_ENV` во время запроса.
Эта и другие особенности описаны на странице [Фреймворки](/ru/docs/frameworks/).

## Запуск Rapira

Запустите Rapira:

```bash
rapira serve --mode worker worker.php
```

`--mode worker` выбирает режим Worker. `127.0.0.1:8000` — стандартный адрес прослушивания.
`rapira serve` работает на переднем плане.

Откройте другой терминал. Отправьте запрос:

```bash
curl -i http://127.0.0.1:8000/
```

Нажмите `Ctrl-C` в первом терминале, чтобы остановить Rapira.

Входной скрипт — `worker.php`, поэтому `$_SERVER['SCRIPT_NAME']` содержит `/worker.php`. Symfony не находит это значение в начале URI.
Затем Symfony задаёт базовый URL как `""`. `getPathInfo()` возвращает путь запроса, и маршрутизация работает правильно.
`generateUrl()` создаёт пути без префикса `/worker.php`. Для этого не нужны переопределения `$_SERVER` или `Request::setTrustedProxies()`.

## Выход в продакшен

Задайте `APP_ENV=prod`. Установите зависимости без пакетов для разработки.
Создайте кеш перед запуском сервера. Тесты подтвердили правильную инициализацию с `php bin/console cache:warmup`.
Эта команда также компилирует контейнер до первого запроса:

```bash
composer install --no-dev --optimize-autoloader
APP_ENV=prod php bin/console cache:warmup
```

Также проверьте `DEFAULT_URI`. В базовом приложении файл `config/packages/routing.yaml` задаёт `router.default_uri` как `%env(DEFAULT_URI)%` во **всех** окружениях. Файл `.env` устанавливает значение `http://localhost`. Symfony использует это значение для URL вне HTTP-запроса, например в консольных командах и письмах. Укажите фактический адрес приложения.

Небольшой `rapira.toml`, чтобы всё это запустить:

```toml
[http]
listen = "127.0.0.1:8000"

[pool]
entrypoint = "worker.php"
mode = "worker"
processes = 4
max_requests = 500
request_terminate_timeout_secs = 30
```

`max_requests` заменяет воркер после заданного числа запросов. Он ограничивает влияние утечки памяти, но не исправляет её.
`request_terminate_timeout_secs` ограничивает время одного запроса.
Запустите сервер командой `APP_ENV=prod rapira serve --config rapira.toml`.
Относительный `entrypoint` использует каталог файла конфигурации. Все настройки описаны в разделе [Конфигурация](/ru/docs/configuration).

## Сброс состояния между запросами

`services_resetter` вызывает `reset()` для каждого сервиса с тегом `kernel.reset`. Набор сервисов зависит от установленных бандлов.
Примеры включают буферизованные обработчики логов и сборщики отладочных данных. Сервисы сами регистрируют этот тег.

Он не сбрасывает статические свойства приложения, глобальные значения, реестры библиотек или постоянные изменения `ini_set()`.
Это состояние остаётся в каждом постоянном воркере. Сбрасывайте его в коде приложения.
Таблица времени жизни состояния находится на странице [Фреймворки](/ru/docs/frameworks/).

Тесты со сбросом показали стабильную память процесса во время 200 последовательных запросов в `dev` и `prod`.
Если память растёт, код приложения или бандл может сохранять состояние запроса.

## Работа после ответа

Вызовите [`rapira_finish_request()`](/ru/docs/http) между `$response->send()` и `$kernel->terminate()`, чтобы отправить ответ до запуска последующих слушателей.
Воркер продолжает выполнять `terminate()` до возврата обработчика. Это может уменьшить ожидание клиента, но не добавляет конкурентность.

## Цикл разработки

`rapira serve` работает на переднем плане и инициализирует приложение один раз. Поэтому **замените воркер для загрузки изменённого кода PHP**.
Перезапускайте сервер после каждого изменения во время разработки. В качестве альтернативы используйте [режим Classic](/ru/docs/classic):

```bash
rapira serve --mode classic public/index.php
```

Это то же самое приложение в режиме Classic. Оно поднимается на каждом запросе, поэтому правки вступают в силу немедленно. При этом полный подъём выполняется для каждого запроса. На работающем боевом сервере выложенный код подхватывает плавная перезагрузка (`SIGUSR2` мастер-процессу). Она позволяет завершить текущие запросы, но закрывает неактивные keep-alive-соединения. Исключение - `opcache.validate_timestamps = 0`: сегмент OPcache принадлежит мастер-процессу и переживает пул, поэтому деплою понадобится полный перезапуск. Подробности - в разделах [Модель процессов](/ru/docs/process-model) и [Запуск в продакшене](/ru/docs/deployment).

Symfony обрабатывает непойманное исключение приложения и возвращает свой ответ `500`. В `dev` он содержит страницу исключения.
В `prod` он содержит общую страницу ошибки. Тот же воркер обрабатывает следующий запрос.
Финальный сброс удаляет изменённое состояние сервисов. Настроенный логгер Symfony управляет выводом исключения. В базовом приложении логгера нет.
Rapira записывает ошибки PHP, которые выходят из фреймворка, например указанное выше `EnvNotFoundException`. Настройка уровней описана в разделе [Логирование](/ru/docs/logging).
