# Yii3

Из трёх фреймворков, о которых здесь написано, Yii3 задумывался ровно под такой сценарий. В его DI-контейнере с самого начала живёт полноценный `StateResetter`, раннер отдаёт свой контейнер через публичное API, а схема «собрать приложение один раз, сбросить состояние запроса после каждого ответа» — не хитрость, придуманная ради долгоживущего сервера, а то, как фреймворк устроен изначально. Официальный раннер для RoadRunner, [`yiisoft/yii-runner-roadrunner`](https://github.com/yiisoft/yii-runner-roadrunner), сделан ровно так же, и это хороший знак: описанная ниже схема — задуманный способ жить в долгоживущем процессе, а не ловкое злоупотребление им.

::: info Проверено на
- **PHP 8.5.8** — NTS, embed SAPI.
- **Rapira 0.6.0**.
- Шаблон **yiisoft/app** 1.4 с **yii-runner-http 3.2.1** (router-fastroute 4.x).

Оба скрипта воркера с этой страницы прогнаны на этом стеке и прошли весь набор проверок: маршрутизация, сгенерированные URL, отправка форм и JSON, сессии, загрузка файлов, обработка ошибок и 200 запросов подряд.
:::

## Почему Yii3 хорошо ложится на ступень воркера

Резидентному воркеру хватает двух вещей из публичного API.

`ApplicationRunner::getContainer()` объявлен публичным — раннер отдаёт вам тот самый контейнер, на котором работает приложение, так что ни наследоваться, ни лезть в приватные поля не нужно. А `Yiisoft\Di\StateResetter` — обычный сервис в этом же контейнере: компоненты регистрируют в нём свои колбэки сброса, и один вызов `reset()` возвращает их в исходное состояние. Это собственный ответ фреймворка на вопрос «что делать с объектом, который держит состояние запроса», и появился он потому, что Yii3 изначально рассчитан на процесс, который не умирает.

Поэтому вся резидентная схема — три строчки связующего кода: собрать раннер один раз, вызывать его на каждый запрос и сбрасывать состояние контейнера после ответа.

## Что понадобится

- Установленная Rapira — см. [Установку](/ru/docs/installation).
- Приложение на Yii3: либо свежий проект из [`yiisoft/app`](https://github.com/yiisoft/app), либо тот, что у вас уже есть.

На стороне PHP ставить нечего: ни пакета-рантайма, ни прослойки, ни адаптера. Скрипт воркера ниже — единственный новый файл в проекте, и лежит он в корне проекта, рядом с `composer.json`, потому что `rootPath` раннера — это как раз корень проекта.

## Резидентный воркер

Это рекомендуемый вариант. Сохраните его как `worker.php` в корне проекта:

```php
<?php

declare(strict_types=1);

use App\Environment;
use Rapira\Plugin\Http\HttpHandlerConfig;
use Yiisoft\Di\StateResetter;
use Yiisoft\Yii\Runner\Http\HttpApplicationRunner;

use function Rapira\create_plugin_handler;

require_once __DIR__ . '/vendor/autoload.php';
require_once __DIR__ . '/src/bootstrap.php';

$runner = new HttpApplicationRunner(
    rootPath: __DIR__,
    debug: Environment::appDebug(),
    checkEvents: Environment::appDebug(),
    environment: Environment::appEnv(),
);
$container = $runner->getContainer();

$http = create_plugin_handler(new HttpHandlerConfig());

$handler = static function () use ($runner, $container): void {
    try {
        $runner->run();
    } finally {
        // The worker keeps serving after an escaped error; the reset has to
        // run on that path too, or state leaks into the next request.
        $container->get(StateResetter::class)->reset();
    }
};

while ($http->handleRequest($handler)) {
    gc_collect_cycles();
}
```

Разберём по частям.

**`src/bootstrap.php` — это собственный бутстрап шаблона.** Он подключает автозагрузчик Composer, читает `.env`, если тот есть, и вызывает `Environment::prepare()` — ровно то же самое делает `public/index.php`, прежде чем взяться за раннер. Строка с `vendor/autoload.php` выше него — подстраховка (это `require_once`, так что она ничего не стоит), заодно скрипт остаётся читаемым как самостоятельная точка входа.

**Раннер создаётся один раз, с теми же аргументами, что и в `public/index.php`.** `rootPath`, `debug`, `checkEvents` и `environment` берутся из `App\Environment` точь-в-точь так, как их передаёт фронт-контроллер, поэтому воркер поднимает то же самое приложение, что и веб-точка входа. Шаблонный `public/index.php` передаёт ещё один аргумент — `temporaryErrorHandler` с логгером через `StreamTarget`, — а при включённом `APP_C3` подключает `c3.php`. В проверенном воркере нет ни того, ни другого. Временный обработчик ошибок ловит только то, что случилось во время сборки конфигурации и контейнера; без него раннер откатывается на `ErrorHandler` с `NullLogger` (`HttpApplicationRunner::createTemporaryErrorHandler()`) — так что передайте его и здесь, если хотите видеть в логах сбои сборки контейнера.

**`getContainer()` — часть публичного API**, поэтому контейнер, который вы забираете себе, и есть контейнер приложения: тот самый, которым раннер будет пользоваться на каждом запросе. `StateResetter` достаётся из него уже внутри обработчика.

**На каждый запрос — `run()`, затем `reset()`.** `run()` — тот же вызов, что делает фронт-контроллер, а `reset()` проходит по зарегистрированным в контейнере колбэкам сброса и возвращает сервисы с состоянием в исходное положение до того, как придёт следующий запрос.

**Резидентный раннер всё равно видит каждый новый запрос.** На этом часто спотыкаются, поэтому скажем прямо: `run()` не запоминает запрос в момент создания объекта. На каждом вызове он просит у контейнера `RequestFactory` и собирает свежий PSR-7-объект `ServerRequest` из `$_SERVER`, `$_GET`, `$_POST`, `$_COOKIE`, `$_FILES` и `php://input`, а Rapira заново наполняет эти суперглобальные переменные перед каждым витком цикла (этот контракт разбирает [Режим воркера](/ru/docs/worker)). Объекты резидентные, запрос каждый раз новый.

**Память не растёт.** За 200 запросов подряд занятая воркером память сколько-нибудь заметно не выросла: приложение собирается один раз, сброс стоит дёшево, и убирать за загрузкой на каждом запросе просто нечего. Это и есть практическая выгода этой схемы по сравнению со следующей.

## Вариант попроще: новый раннер на каждый запрос

Если про резидентное состояние думать вообще не хочется, создавайте раннер *внутри* обработчика. Тогда всё, что построит приложение, принадлежит одному запросу:

```php
<?php

declare(strict_types=1);

use App\Environment;
use Rapira\Plugin\Http\HttpHandlerConfig;
use Yiisoft\Yii\Runner\Http\HttpApplicationRunner;

use function Rapira\create_plugin_handler;

require_once __DIR__ . '/vendor/autoload.php';
require_once __DIR__ . '/src/bootstrap.php';

$http = create_plugin_handler(new HttpHandlerConfig());

$handler = static function (): void {
    // A fresh runner per request; constructor arguments mirror public/index.php.
    $runner = new HttpApplicationRunner(
        rootPath: __DIR__,
        debug: Environment::appDebug(),
        checkEvents: Environment::appDebug(),
        environment: Environment::appEnv(),
    );
    $runner->run();
};

while ($http->handleRequest($handler)) {
    gc_collect_cycles();
}
```

Меньше подвижных частей, нечего сбросить неправильно, и состоянию неоткуда протечь из одного запроса в следующий: контейнер каждый раз собирается заново. Этот вариант тоже прошёл весь набор проверок.

Цена честная, и именно из-за неё эта схема идёт на странице *второй*: контейнер поднимается на каждый запрос, а значит, за подъём вы платите каждый раз и каждый раз производите целый контейнер мусора. Память воркера растёт, пока эти контейнеры копятся и PHP не освободит их разом, — обычная картина для загрузки на каждом запросе, а не утечка, но и её стоит ограничить сверху. Поставьте рядом с этой схемой `pool.max_requests`, чтобы воркер время от времени завершался и уступал место новому: как ведёт себя память в разных случаях, разбирает [обзор фреймворков](/ru/docs/frameworks/), а сам ключ описан в [Конфигурации](/ru/docs/configuration).

Автозагрузчик и бутстрап шаблона всё равно остаются резидентными, а цикл по-прежнему ваш, так что это именно воркер, который сам решил выбрасывать приложение между запросами, а не [классический режим](/ru/docs/classic).

## Как это запустить

```bash
rapira serve worker.php
```

Это вся команда: режим воркера включён по умолчанию. Остальные флаги собраны в разделе [Командная строка](/ru/docs/cli).

Для продакшена перенесите настройки в `rapira.toml`:

```toml
[http]
listen = "127.0.0.1:8000"

[pool]
entrypoint = "/srv/app/worker.php"
processes = 8
max_requests = 500
request_terminate_timeout_secs = 30

[log]
level = "info"
format = "json"
```

Каждый ключ вместе со значением по умолчанию и допустимыми границами описан на странице [Конфигурация](/ru/docs/configuration), а юнит systemd и обратный прокси перед сервером ждут в разделе [Запуск в продакшене](/ru/docs/deployment).

## Что проверено

Обе схемы прогнали через один и тот же набор проверок на шаблоне `yiisoft/app`. Вот что из этого вышло.

**Маршрутизация работает без ковыряния в `$_SERVER`.** Rapira кладёт в `SCRIPT_NAME` имя файла входного скрипта — `/worker.php`, а не `/index.php`, — и FastRoute всё равно попадал во вложенные пути со строкой запроса. Корень `/` отдавал домашнюю страницу шаблона, а неизвестный путь — родной 404 фреймворка. Переопределять `SCRIPT_NAME`, `REQUEST_URI` или `DOCUMENT_ROOT` нигде не пришлось.

**Сгенерированные URL чистые.** `UrlGeneratorInterface::generate()` выдавал обычные пути приложения — имя файла скрипта воркера в них не просачивается.

**Сессии живут по запросам и честно изолированы.** Клиент, который хранит куки, видел, как его счётчик идёт 1, 2 от запроса к запросу, а новый клиент, постучавшийся сразу после в тот же эндпоинт, получил свежую сессию и снова начал с 1. В резидентной схеме, где контейнер переживает запрос, всё точно так же.

**Формы, JSON-тела и загруженные файлы доходят целиком.** Поля `$_POST`, JSON из `php://input`, multipart-загрузка с временным файлом, который читается прямо во время запроса, — всё это лежит в PSR-7-объекте `ServerRequest`, который yii-runner-http собирает из суперглобальных переменных.

**Брошенное исключение превращается в 500, а воркер продолжает обслуживать запросы.** Исключение из действия ловит `ErrorCatcher` и рисует страницу ошибки ровно так же, как в любом другом окружении; исключение попадает в лог, а следующий же запрос тот самый процесс воркера обслуживает как ни в чём не бывало. В Rapira непойманное исключение — сбой одного запроса, а не всего воркера; что уносит воркер, а что нет, разбирает [Режим воркера](/ru/docs/worker).

## CSRF остаётся в силе

В шаблоне приложения `CsrfTokenMiddleware` стоит в цепочке middleware по умолчанию, а токен лежит в сессии — том самом состоянии, которое проверки как раз погоняли: своё на каждый запрос и изолированное для каждого клиента. Цикл воркера в работу с токеном никак не вмешивается, поэтому POST требует здесь токен ровно так же, как и везде. Если после переезда на воркер запросы начали отлетать, токен — первое, что стоит проверить, и лечится это обычным способом (отрисовать токен в форму и отправить обратно), а не правкой скрипта воркера.

## Запасной выход: классический режим

Если воркер вам сейчас не нужен, Yii3 прекрасно работает и обычным фронт-контроллером:

```bash
rapira serve --classic public/index.php
```

Тот же код, никакого скрипта воркера, чистое состояние на каждый запрос — что даёт эта ступень и чем за неё платят, разбирает [Классический режим](/ru/docs/classic).

Одна любопытная деталь, если вы всё-таки заглянете в этот файл: в шаблонном `public/index.php` есть ветка `PHP_SAPI === 'cli-server'`, которая отдаёт статику и переписывает `SCRIPT_NAME`. Она написана для встроенного сервера разработки PHP и под Rapira просто никогда не срабатывает, потому что `PHP_SAPI` здесь — `rapira` (на PHP 8.4 — `fastcgi`, см. [Установку](/ru/docs/installation)). Не трогайте её: тут она мертва.

::: question Какую схему выбрать?
Резидентную, если нет причин поступить иначе. Это собственная схема фреймворка для долгоживущего процесса: память не растёт, а весь сброс — один вызов. Раннер на каждый запрос пригодится, когда в вашей загрузке есть требования к порядку, о которых не хочется думать: код, который обязан отработать до сборки контейнера, или подготовка на каждый запрос, которую колбэк `StateResetter` откатить не сможет. Начать можно и с него, а подняться выше позже — меняется только скрипт воркера.
:::

::: question В резидентной схеме `checkEvents` и остальная загрузка выполняются на каждом запросе?
Да: `run()` каждый раз прогоняет свою внутреннюю последовательность — регистрация обработчика ошибок, `runBootstrap()`, `checkEvents()`, затем обработка запроса. На 200 вызовах подряд это оказалось безвредным: раннер по замыслу можно вызывать повторно. Проверка событий вообще что-то делает, только когда поднят её флаг, а в шаблоне этот флаг — `Environment::appDebug()`, так что с выключенной отладкой она на каждом вызове ничего не стоит.
:::

::: question `public/index.php` всё ещё нужен?
Оставьте его. Он ничего не стоит, именно к нему вы вернётесь в [классическом режиме](/ru/docs/classic), и он по-прежнему удобен для локальной работы со встроенным сервером PHP. Скрипт воркера — дополнительная точка входа, а не замена фронт-контроллеру.
:::

::: question Что именно сбрасывает `StateResetter::reset()`?
Ровно то, что зарегистрировали в нём сервисы вашего контейнера, — в этом и смысл того, что он сервис контейнера, а не хук фреймворка. Компоненты Yii3, хранящие состояние, регистрируют свои колбэки сами; если вы пишете сервис, который держит состояние запроса, зарегистрируйте и свой — ключ `'reset' => function (): void { … }` в DI-описании этого сервиса, ровно так же, как объявляют свои `yiisoft/session` и `yiisoft/router`. Замыкание привязано к экземпляру, поэтому оно может восстановить приватное состояние, не пересобирая объект. Что между запросами сбрасывает сама Rapira и что она намеренно оставляет как есть, описано в [обзоре фреймворков](/ru/docs/frameworks/) и в разделе [Режим воркера](/ru/docs/worker).
:::
