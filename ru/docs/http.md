# Запросы и ответы HTTP

HTTP-сервер преобразует соединение клиента в запрос PHP, а ответ PHP — в сетевые данные.
Он использует библиотеку [hyper](https://hyper.rs) внутри бинарного файла Rapira. Он принимает HTTP/1.1 и HTTP/1.0 на сокете мастер-процесса.
Сервер разбирает запрос, передаёт его PHP и отправляет ответ. Он не перенаправляет запросы другому серверу.
Middleware может ответить до запуска PHP. Так Rapira отдаёт [статические файлы](/ru/docs/static-files).

Эта страница описывает проверку запросов, преобразование полей `$_SERVER`, повторяющиеся поля, ограничения тела и границы ответа.

::: info
HTTP-сервер принимает незашифрованный HTTP. Используйте прокси для завершения TLS. См. раздел [Запуск в продакшене](/ru/docs/deployment).
:::

## Проверка запроса

HTTP-сервер проверяет каждый запрос до запуска PHP. При ошибке проверки сервер отвечает без вызова PHP.

Rapira возвращает `501` для запроса `CONNECT`. HTTP-сервер не создаёт туннели.

Rapira принимает абсолютную форму цели, например `GET http://host.example/admin?x=1 HTTP/1.1`. Authority цели заменяет поле `Host`.
Rapira сначала удаляет из authority данные пользователя. Это предотвращает конфликт в `$_SERVER['HTTP_HOST']`.
PHP получает путь и строку запроса в `$_SERVER['REQUEST_URI']`.

`http.keepalive_timeout_secs` ограничивает каждое чтение от клиента. Ограничение действует на неактивное соединение и заголовки запроса.
Rapira возвращает `408`, если чтение тела не продолжается до истечения времени. Затем сервер закрывает соединение.
Значение по умолчанию — 60 секунд.

```toml
[http]
keepalive_timeout_secs = 60
```

## От имени заголовка к ключу `$_SERVER`

CGI переводит имя поля запроса в верхний регистр. Он заменяет каждый `-` на `_` и добавляет `HTTP_`.
См. [RFC 3875 §4.1.18](https://www.rfc-editor.org/rfc/rfc3875#section-4.1.18). Поэтому `X-Forwarded-For` становится `HTTP_X_FORWARDED_FOR`.

При регистрации переменной PHP также заменяет `.` на `_`.
Поэтому три разных сетевых имени соответствуют одному ключу PHP:

| В запросе         | В PHP                               |
| ----------------- | ----------------------------------- |
| `X-Forwarded-For` | `$_SERVER['HTTP_X_FORWARDED_FOR']`  |
| `X_Forwarded_For` | `$_SERVER['HTTP_X_FORWARDED_FOR']`  |
| `X.Forwarded.For` | `$_SERVER['HTTP_X_FORWARDED_FOR']`  |

::: warning
Без обязательной проверки имён полей Rapira такое совпадение может создать угрозу безопасности. Прокси может задать `X-Forwarded-For`, а клиент — отправить `X_Forwarded_For`.
Оба имени соответствуют одному ключу `$_SERVER`. Фильтр прокси для имени с дефисами может не удалить имя с подчёркиваниями.
В результате приложение может принять значение клиента за значение прокси.
:::

## Имена, конфликтующие с CGI-переменной

Rapira проверяет имена полей до другой обработки. Он принимает только байты из `[A-Za-z0-9-]`.
Символы `_` и `.` могут соответствовать тому же ключу `$_SERVER`, что и `-`. Список также отклоняет другие символы, например `~`.
Параметр `http.unsafe_field_names` задаёт обработку отклонённых имён:

- **`drop`** (по умолчанию) - поле удаляется до того, как его увидит PHP, и каждое удаление пишется в лог с уровнем `warn` в цель `http`.
- **`reject`** - запрос получает `400` и не обслуживается вовсе.

```toml
[http]
unsafe_field_names = "drop"
```

Проверку нельзя выключить. Также нельзя добавить исключения для отдельных имён.
Полный список настроек см. в разделе [Конфигурация](/ru/docs/configuration).

Замените подчёркивания в обязательном имени поля на дефисы. Rapira применяет это правило и к полям от прокси.
Rapira не может определить источник поля с подчёркиванием. Настройте прокси для изменения имени перед отправкой.

::: tip
`drop` записывает каждое удаление с уровнем `warn`, но уровень по умолчанию — `error`.
Установите для цели `http` уровень `warn`, чтобы видеть эти записи. См. раздел [Логирование](/ru/docs/logging).
:::

## Поля, присланные несколько раз

HTTP разрешает повторяющиеся поля, но CGI предоставляет одно значение для каждой переменной. Rapira объединяет значения по синтаксису поля:

- **Списочные поля:** Rapira соединяет значения запятой и пробелом. См. [RFC 9110 §5.3](https://www.rfc-editor.org/rfc/rfc9110#section-5.3).
- Например, две строки `Accept` становятся `text/*, image/*`.
- **`Cookie`:** Rapira соединяет значения точкой с запятой и пробелом. Такой формат ожидает парсер cookie PHP.
- **Поля с одним значением:** Rapira сохраняет первую строку `Authorization`, `Proxy-Authorization`, `Content-Type`, `Referer` или `From`.
- Дополнительные строки удаляются с записью `warn`. Повторный `Content-Length` получает ответ `400` до этой обработки.
- **`Host`:** Rapira возвращает `400` для нескольких строк `Host`. См. [RFC 9112 §3.2](https://www.rfc-editor.org/rfc/rfc9112#section-3.2).

PHP получает значения полей как неизменённые байты. Поэтому cookie в Latin-1 или подписанное поле сохраняет каждый байт клиента.

## Тела запросов

Rapira читает тело запроса в память до запуска PHP. `http.max_body_size_mb` ограничивает память для одного тела.
Значение по умолчанию — 8 МиБ, как у `post_max_size` в PHP.
Rapira возвращает `413` для большего тела и закрывает соединение. Оставшиеся данные тела сервер не читает.

Лимит проверяется дважды:

- Сначала Rapira проверяет объявленный `Content-Length` до чтения тела.
- Затем сервер проверяет каждый фрагмент тела. Эта проверка ограничивает chunked-запросы без объявленной длины.

Rapira поддерживает `Expect: 100-continue` для HTTP/1.1. Он отправляет `100 Continue` перед передачей тела клиентом.
Rapira сначала проверяет `Content-Length`. Поэтому сервер может вернуть `413` до загрузки слишком большого тела.
Для HTTP/1.0 ожидание игнорируется согласно [RFC 9110 §10.1.1](https://www.rfc-editor.org/rfc/rfc9110#section-10.1.1).

```toml
[http]
max_body_size_mb = 8
```

## Передача ответа

HTTP-сервер не буферизует тело ответа. Он отправляет заголовки после их фиксации в PHP.
Затем сервер отправляет каждый фрагмент тела, когда PHP его создаёт. Режим определяет время передачи данных.
В режимах Classic и Worker PHP обычно передаёт полный ответ в конце запроса. `rapira_finish_request()` передаёт его раньше.
В режиме Dispatcher PHP передаёт заголовки и фрагменты по мере их записи.

Сервер задаёт границы ответа. Он удаляет поля `Transfer-Encoding` и `Content-Length`, которые установил PHP.
В режимах Classic и Worker сервер устанавливает длину полного тела PHP.
В режиме Dispatcher сервер использует объявленный PHP `Content-Length` и сравнивает его с длиной тела.
При коротком теле сервер закрывает соединение. Длинное тело он обрезает до объявленной длины.

Для ответа без длины сервер использует chunked transfer coding в HTTP/1.1. В HTTP/1.0 он закрывает соединение после тела.

Сервер не добавляет `Content-Length` в ответы `204` и `304`. В ответе `HEAD` он также удаляет это поле и тело.

Сервер удаляет поля конкретного соединения, которые установил PHP. Это поведение определяет [RFC 9110 §7.6.1](https://www.rfc-editor.org/rfc/rfc9110#section-7.6.1):

`Connection`, `Keep-Alive`, `Upgrade`, `Trailer`, `TE`, `Proxy-Connection`, а также два поля, задающие границы тела, - `Content-Length` и `Transfer-Encoding`.

Если PHP отправляет `Connection`, Rapira также удаляет указанные в нём поля. Это происходит до добавления собственного `Content-Length`.
Поэтому `Connection: content-length` не может удалить границы ответа.

Другие поля PHP сервер отправляет без изменений. Это относится и к повторяющимся `Set-Cookie`, `Vary` и `Link`.
Недопустимое сетевое поле сервер удаляет и записывает в лог. Остальная часть ответа отправляется.

Rapira удаляет промежуточные заголовки и трейлеры от PHP. Ответ `100 Continue` для запроса `Expect` создаёт HTTP-сервер.

Если воркер завершает работу до конца тела, сервер закрывает соединение без завершающего маркера.
Сервер также закрывает соединение, если тело короче длины, объявленной PHP.
Фатальная ошибка после начала вывода может завершить скрипт и прервать ответ.
В режиме Worker непойманное исключение обработчика после начала вывода прерывает ответ, но цикл продолжается.
Каждый случай создаёт неполное сообщение, которое может обнаружить клиент.

Ответ HTTP-сервера об ошибке не имеет тела. Он содержит `cache-control: private, no-store` и `connection: close`.
Примеры: `413` для большого тела и `501` для `CONNECT`.

::: question Почему поля, задающие границы тела, выставляет фронт, а не PHP?
HTTP-сервер сравнивает размер тела с объявленной длиной. При коротком теле он закрывает соединение.
Это не даёт клиенту принять следующий ответ за часть текущего. Поле PHP `Content-Length` удаляется, потому что оно может обойти подсчёт.
:::

## Досрочное завершение ответа

Обработчик может продолжить работу после подготовки ответа. Например, он может отправить webhook, добавить задачу в очередь или обновить кеш.
Клиент не должен ждать эту работу.

`rapira_finish_request()` завершает ответ в этой точке. PHP очищает буферы вывода и передаёт ответ HTTP-серверу.
HTTP-сервер отправляет ответ, пока обработчик продолжает работу. Функция имеет тот же контракт, что и `fastcgi_finish_request()`:

```php
<?php

header('Content-Type: text/plain');
echo "Order accepted\n";

rapira_finish_request();

// This code runs after the client receives the response.
$mailer->sendConfirmation($order);
$metrics->flush();
```

Сигнатура — `rapira_finish_request(): bool`.
Файл [`crates/php_sys/rapira.stub.php`](https://github.com/rapira-rs/rapira/blob/main/crates/php_sys/rapira.stub.php) объявляет её и другие API PHP.
Добавьте этот файл в IDE для автодополнения и информации о типах.

Rapira регистрирует функцию для всего процесса. Функция действует на текущий запрос.
Поэтому режим Classic также поддерживает её. См. [Режимы выполнения](/ru/docs/execution-modes).

Функция имеет следующие ограничения:

- **Вывод после вызова не отправляется.** Rapira удаляет вывод после закрытия ответа.
- Запишите весь необходимый вывод до вызова.
- **Воркер остаётся занят.** Он не принимает следующий запрос до завершения обработчика.
- Вызов уменьшает задержку клиента, но не увеличивает параллелизм. Передавайте длительную работу в очередь.
