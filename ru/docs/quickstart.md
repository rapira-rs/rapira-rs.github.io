# Быстрый старт

Эта страница продолжает [Установку](/ru/docs/installation): у вас уже есть рабочий бинарник `rapira` и PHP, который идёт с ним в комплекте. За несколько минут вы отдадите первую страницу в классическом режиме, превратите то же приложение в резидентный воркер и перенесёте настройки в файл конфигурации.

## Hello world в классическом режиме

Классический режим — ступень, доступная любому приложению: Rapira заново подключает ваш входной скрипт на каждый запрос, ровно так же, как php-fpm выполняет фронт-контроллер. Код при этом менять не нужно, поэтому начинать удобно именно отсюда.

Создайте `public/index.php`:

```php
<?php
header('Content-Type: text/plain');
echo "Hello, " . ($_GET['name'] ?? 'anonymous') . "!\n";
echo "Method: {$_SERVER['REQUEST_METHOD']}\n";
```

Теперь запустите сервер. Флаг `--classic` выбирает режим, а входной скрипт передаётся позиционным аргументом:

```bash
rapira serve --classic public/index.php
```

Если не сказать иначе, Rapira слушает `127.0.0.1:8000`. Из другого терминала:

```bash
curl '127.0.0.1:8000/?name=world'
```

```
Hello, world!
Method: GET
```

Процесс между запросами никуда не девается: Rapira один раз форкает воркеров и держит внутри каждого поднятый интерпретатор PHP. Выбрасывается другое — состояние самого скрипта: переменные, автозагрузчик, всё, что успел построить фреймворк. Это компромисс классического режима, и именно поэтому существует следующая ступень.

## То же приложение резидентным воркером

Ступень SAPI Worker оставляет скрипт живым. Он поднимается один раз, а дальше в цикле получает от Rapira очередной запрос; Rapira заново наполняет суперглобальные переменные и вызывает ваш обработчик. Код PHP выглядит привычно: вы всё так же читаете `$_GET` и отдаёте ответ через `echo`. Разница в том, что приложение поднимается один раз на процесс, а не на каждый запрос. Про всю лестницу режимов рассказывают [Режимы выполнения](/ru/docs/execution-modes).

Создайте `worker.php` в корне проекта:

```php
<?php
use Rapira\Plugin\Http\HttpHandlerConfig;
use function Rapira\create_plugin_handler;

$http = create_plugin_handler(new HttpHandlerConfig());

// Outside the loop, so it survives every request this worker serves.
$handled = 0;

$handler = static function () use (&$handled): void {
    $handled++;
    header('Content-Type: text/plain');
    echo "Hello, " . ($_GET['name'] ?? 'anonymous') . "!\n";
    echo "worker " . getmypid() . " handled {$handled} request(s)\n";
};

while ($http->handleRequest($handler)) {
    gc_collect_cycles();
}
```

`create_plugin_handler()` запрашивает у сервера обработчик, который занимается HTTP, а `HttpHandlerConfig` говорит, какой именно нужен. Дальше `handleRequest()` блокируется до прихода запроса, выполняет для него ваш колбэк и возвращает `true`; когда сервер начинает останавливаться, он возвращает `false` — на этом цикл и заканчивается.

Сначала остановите классический сервер: нажмите `Ctrl-C` в его терминале, ведь оба слушают один и тот же адрес `127.0.0.1:8000`. Режим воркера включён по умолчанию, так что флаг в этот раз не нужен:

```bash
rapira serve worker.php
```

```bash
curl '127.0.0.1:8000/?name=world'
```

Повторите `curl` несколько раз: счётчик растёт, потому что запросы обслуживает один и тот же процесс. По умолчанию Rapira форкает по воркеру на каждое процессорное ядро, поэтому запрос может попасть в любой из них — какой воркер его примет, решает операционная система. Счётчик у каждого воркера свой, а pid в ответе показывает, кто именно ответил. Если хочется одной аккуратной последовательности, запустите `rapira serve --processes 1 worker.php`. О том, как супервизор присматривает за пулом, рассказывает [модель процессов](/ru/docs/process-model).

Всё, что вы построили до цикла `while`, остаётся в памяти на всё время жизни воркера: автозагрузчик Composer, DI-контейнер, соединения с базой данных и кешем, скомпилированные маршруты и шаблоны. За это вы платите один раз, при старте, а не на каждом запросе. Заново создаётся только то, что относится к конкретному запросу.

::: warning
Состояние, которое остаётся между запросами, теперь ваша ответственность. Статическое свойство, глобальная переменная, незакрытая транзакция — всё, что оставил после себя один запрос, достанется следующему. На что здесь смотреть и как держать воркер в чистоте, разбирает [Режим воркера](/ru/docs/worker).
:::

Внутри обработчика вам доступен привычный набор: `header()`, `http_response_code()`, `echo`, а ещё `rapira_finish_request()` — она отдаёт ответ раньше времени и позволяет продолжить работу после этого. Всё это описано в разделе [HTTP](/ru/docs/http).

## Перенесите настройки в файл конфигурации

Пока вы экспериментируете, флагов вполне хватает, но развёрнутое приложение обычно хранит настройки в файле. Для начала достаточно `rapira.toml` рядом с кодом:

```toml
[http]
listen = "127.0.0.1:8000"

[pool]
entrypoint = "worker.php"
processes = 4
```

```bash
rapira serve --config rapira.toml
```

::: info
Относительный `pool.entrypoint` считается от каталога самого файла конфигурации, поэтому один и тот же файл работает из любого текущего каталога. Флаги по-прежнему сильнее файла: `rapira serve --config rapira.toml --processes 1` оставит остальные настройки как есть и поднимет всего один воркер.
:::

Эти пять строк — лишь малая часть того, что понимает файл: режимы масштабирования пула, пересоздание воркеров, таймауты запросов, логирование, pidfile супервизора. Незнакомые ключи не игнорируются, а отвергаются, поэтому опечатка прерывает запуск, а не остаётся без всякого эффекта. Полный справочник — в [Конфигурации](/ru/docs/configuration), а флаги — в разделе [Командная строка](/ru/docs/cli).

## Остановка сервера

Нажмите `Ctrl-C`, и Rapira уйдёт в мягкое завершение: перестанет брать новую работу, даст доработать уже начатым запросам, выключит расширения и выйдет. Второй `Ctrl-C` пропускает ожидание и завершает процесс принудительно — это помогает, когда запрос завис и ждать его окончания не хочется. `SIGTERM` ведёт себя точно так же, поэтому перезапуск из менеджера служб проходит аккуратно. Полная таблица сигналов, включая перезагрузку без разрыва соединений, есть в разделе [Модель процессов](/ru/docs/process-model).

::: question Нужен ли Composer, чтобы запустить скрипт воркера?
Нет. `create_plugin_handler()`, `HttpHandlerConfig` и классы обработчиков живут в PHP-модуле, который Rapira регистрирует при старте интерпретатора, так что скрипт выше работает вообще без автозагрузчика. Настоящее приложение, разумеется, подключит свой `vendor/autoload.php` — до цикла, чтобы заплатить за это один раз.
:::

::: question Может ли один скрипт работать и в классическом режиме, и в режиме воркера?
Нет, и ошибка будет явной: вне режима воркера `create_plugin_handler()` бросает `Rapira\RapiraException`, потому что в классическом режиме нет резидентного цикла, который можно было бы вам отдать. Оставьте обычный фронт-контроллер для классического режима, а для воркера заведите отдельный `worker.php`; как это связывается в каждом конкретном фреймворке, показывают [руководства по фреймворкам](/ru/docs/frameworks/).
:::
