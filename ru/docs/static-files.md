# Статические файлы

Rapira отдаёт файлы из каталога через middleware статических файлов, ещё до того, как запрос дойдёт до PHP. Этот middleware стоит в HTTP-фронте перед обработчиком PHP: запрос, который указывает на файл под его корневым каталогом, он обслуживает сам, а все остальные передаёт дальше по цепочке нетронутыми.

## Как включить middleware

Включают его две части `rapira.toml`: имя `static` в списке middleware секции `[http]` и секция `[http.static]`, которая говорит, где лежат файлы.

```toml
[http]
middleware = ["static"]

[http.static]
root = "public"     # required; a relative path resolves against this file's directory
forbid = [".php"]   # optional; an explicit list replaces this default
```

`middleware` задаёт цепочку middleware в том порядке, в каком они перечислены. Сейчас `static` — единственное имя, которое он принимает.

`root` называет каталог, из которого middleware отдаёт файлы. Значения по умолчанию у него нет, поэтому секция обязана его задать. Относительный путь считается от каталога с файлом конфигурации — так же, как у `pool.entrypoint`.

`forbid` перечисляет расширения, которые middleware не отдаёт никогда. По умолчанию это `[".php"]`, и явный список заменяет умолчание целиком: `forbid = [".php", ".env"]` закрывает оба расширения, а `forbid = []` отдаёт под корнем всё подряд, включая исходники PHP. Каждый элемент — расширение с точкой в начале, длиной не меньше двух символов, без `/` и без пробельных символов. Элемент другой формы останавливает запуск.

Остальные ключи файла собраны на странице [Конфигурация](/ru/docs/configuration).

::: question Почему элемент `forbid` обязан выглядеть как расширение?
Middleware сравнивает каждый элемент с концом имени файла. Ни разделитель, ни пробел не могут оказаться в конце имени, поэтому элемент с таким символом не совпадёт ни с чем, а файл, который он должен был закрыть, останется доступным. Проверка отвергает такой элемент, вместо того чтобы принять защиту, которая ничего не защищает.
:::

## Проверки при запуске

Корневой каталог сервер проверяет до того, как начнёт что-либо отдавать. Каталог должен существовать, должен быть именно каталогом и должен быть доступен на поиск пользователю, от имени которого работает сервер. Корень, не прошедший одну из этих проверок, останавливает запуск сообщением, в котором назван путь.

Две части конфигурации обязаны сходиться друг с другом. `middleware = ["static"]` без секции `[http.static]` останавливает запуск, и секция `[http.static]`, которой нет в списке `middleware`, останавливает запуск тоже. Имя, указанное в `middleware` дважды, отвергается точно так же.

::: question Почему сервер проверяет корневой каталог дважды?
Первая проверка читает метаданные корня и показывает, что путь существует и что это каталог. Вторая разрешает `.` внутри корня и показывает право на поиск, без которого не обойдётся ни одно чтение под этим каталогом. Право на поиск в каталоге — отдельный бит, не совпадающий с правом на чтение, поэтому корень, прошедший первую проверку, вполне может не пройти вторую. Какие права нужны каждому вызову, описывает [`stat`](https://pubs.opengroup.org/onlinepubs/9799919799/functions/stat.html).
:::

## Правила отдачи

Middleware берётся за запрос только тогда, когда метод — `GET` или `HEAD`. Любой другой метод уходит в PHP.

Дальше всё решает путь:

- Путь, в котором сегмент начинается с `.`, уходит в PHP, поэтому `/.env`, `/.git/config` и `/../outside.txt` до файловой системы не доходят.
- Проверка `forbid` идёт по пути с раскрытыми процентными последовательностями и сравнивает последний сегмент без учёта регистра, поэтому при `.php` в `forbid` в PHP уходят и `/index.php`, и `/index%2Ephp`, и `/Upper.PHP`.
- URL каталога уходит в PHP. Индексный файл middleware для него не отдаёт — ни с завершающей косой чертой, ни без неё.
- Путь, за которым нет файла, уходит в PHP. Ошибка прав доступа тоже уходит в PHP, как и имя, которое файловая система не принимает.
- Любая другая ошибка чтения даёт ответ `500`. Такой запрос до PHP не доходит, а сама ошибка пишется в лог в цель `http`.

Запрос, ушедший в PHP, доходит до него неизменным: то же тело, те же поля, те же прикреплённые к запросу данные. Что именно читает из него PHP, разбирает раздел [Запросы и ответы HTTP](/ru/docs/http).

::: question Почему на URL каталога не приходит `index.html`?
Пространство URL принадлежит PHP: URL каталога — это маршрут приложения. Неявный индексный файл дал бы на один URL два ответа, один из файловой системы и один от маршрутизатора, и заодно отобрал бы `/` у фронт-контроллера.
:::

::: question Как middleware отличает промах от ошибки чтения?
Шесть исходов означают, что отдавать нечего: пути не существует, процессу нельзя его читать, путь оказался каталогом, компонент пути не является каталогом, имя слишком длинное для файловой системы, в имени есть нулевой байт. Каждый из них — промах, и запрос идёт дальше в PHP. Любая другая ошибка сообщает о файле, который существует и не читается, а на такое и PHP не ответит, поэтому middleware отдаёт `500`.
:::

## Поля ответа

Перечисленные ниже поля относятся к ответу, который отдаёт файл. В ответе `500`, который формирует сам middleware, их нет.

`Content-Type` middleware выставляет по расширению файла. Имя с неизвестным расширением получает `application/octet-stream`.

В ответе есть поля `ETag` и `Last-Modified`. Оба middleware строит из времени изменения файла. Файл без времени изменения не получает ни одного из них, а файл с временем изменения раньше начала эпохи остаётся без `ETag`.

Middleware отвечает `304 Not Modified`, когда поле `If-None-Match` или `If-Modified-Since` в запросе совпадает с файлом. В таком ответе есть только `ETag` и `Last-Modified`, а тела нет.

В ответе есть и `Accept-Ranges: bytes`. Запрос с полем `Range` получает `206 Partial Content` вместе с полем `Content-Range`. Диапазон, которого файл не покрывает, получает `416 Range Not Satisfiable`, и такой запрос до PHP тоже не доходит.

## Кеш файлов

Каждый рабочий процесс держит отданные файлы в памяти. Настроек у кеша нет, приведённые ниже величины зафиксированы.

Запись остаётся свежей одну секунду. Первый запрос после этого окна выполняет `stat` и обновляет запись, если время изменения и длина по-прежнему совпадают с файлом. Изменившийся файл читается заново.

Файл больше 256 КиБ в кеш не попадает никогда. Такой файл на каждом запросе читается с диска.

Один воркер хранит не больше 16 МиБ. Кеш, дошедший до этого предела, продолжает отдавать то, что уже держит, и сначала выбрасывает свои устаревшие записи, а отказывает новому файлу только после этого. Значит, расход памяти — до 16 МиБ на каждый процесс из `pool.processes`. Перезапуск опустошает кеш.

Свои записи каждый воркер обновляет сам, поэтому изменение под корневым каталогом доходит до клиента не позже чем через секунду. Удалённый и заменённый файл покидают кеш в пределах того же окна. Одна лишь смена прав запись из кеша не убирает, потому что `stat` сообщает прежние время изменения и длину: чтобы убрать такой файл из кеша, удалите его, замените или перезапустите сервер.

Корневой каталог должен лежать на локальном хранилище. `stat` и `open` middleware выполняет в том же потоке рантайма, который обслуживает запросы, поэтому файловая система, отвечающая на эти вызовы медленно, задерживает и остальные соединения этого воркера.

::: question Как кеш замечает, что файл изменился?
Он сравнивает время изменения и длину файла с двумя сохранёнными значениями, и та же пара закодирована в ETag. Замену, после которой оба значения остались прежними, кеш не заметит, поэтому деплой, копирующий файлы, обязан оставлять на каждом заменённом файле новое время изменения или новую длину.
:::
