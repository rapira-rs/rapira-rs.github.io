# Режим Worker

Режим Worker сохраняет процесс PHP между запросами. Скрипт инициализирует приложение один раз, а затем ожидает запросы в цикле. Состояние приложения также остаётся в памяти, поэтому скрипт воркера должен им управлять.

В [режиме Classic](/ru/docs/classic) входной скрипт выполняется в новом запросе PHP. Сервер удаляет состояние приложения после ответа. Это состояние включает автозагрузчик, контейнер, конфигурацию, маршруты и соединения с базой данных.

Эта страница содержит руководство по программированию для режима Worker. Режим Worker не требует определённого фреймворка. Приложение должно обрабатывать много запросов после одной инициализации. Требования к режимам описаны в разделе [Режимы выполнения](/ru/docs/execution-modes). Руководства по фреймворкам находятся в разделе [Фреймворки](/ru/docs/frameworks/).

## Резидентный цикл

Скрипт воркера состоит из трёх частей. Первая часть инициализирует приложение. Вторая часть определяет обработчик одного запроса. Третья часть запускает обработчик до остановки воркера. Используйте `\Rapira\handle_request()` в цикле PHP.

```php
<?php
// worker.php
require __DIR__ . '/vendor/autoload.php';

$app = new App(); // The worker creates this object once and reuses it.

$handler = static function () use ($app): void {
    header('Content-Type: text/plain');
    http_response_code(200);
    echo $app->handle($_SERVER['REQUEST_URI']);
};

while (\Rapira\handle_request($handler)) {
    gc_collect_cycles();
}
```

Dispatcher — режим по умолчанию. Выберите режим Worker одним из этих способов:

- `--mode worker` в командной строке, рядом с входным скриптом.
- `mode = "worker"` в секции `[pool]` файла `rapira.toml`.

```bash
rapira serve --mode worker app/worker.php
```

Остальные флаги собраны в разделе [Командная строка](/ru/docs/cli), а их аналоги для `rapira.toml` - в [Конфигурации](/ru/docs/configuration).

## Контракт `handle_request()`

`\Rapira\handle_request(callable $handler): bool` имеет следующий контракт:

- **Ожидает** запрос для этого воркера. Во время ожидания воркер не использует процессор.
- Воркер сохраняет интерпретатор и инициализированное приложение в памяти.
- **Заполняет данные запроса** в `$_GET`, `$_POST`, `$_SERVER`, `$_COOKIE`, `$_FILES` и `$_REQUEST` до запуска обработчика.
- Обычный код PHP может читать их так же, как под php-fpm.
- **Вызывает обработчик без аргументов.** Данные запроса находятся в суперглобальных переменных. Сигнатура функции — `function (): void`.
- Захватите контейнер, логгер и другие зависимости с помощью `use`.
- **Использует вывод обработчика как ответ.** Обработчик может вызывать `echo`, `print`, `header()`, `http_response_code()` и `setcookie()`.
- Обработка запросов и ответов описана в разделе [HTTP](/ru/docs/http).
- **Возвращает `true`** после запроса, поэтому цикл продолжается. Функция возвращает **`false`** при остановке воркера.
- Завершите цикл и скрипт после возврата `false`.
- **Вызывайте функцию только из цикла верхнего уровня.** Не вызывайте её из shutdown-функции или деструктора.

Один запрос в режиме Worker соответствует одной итерации цикла `while`. Rapira завершает запрос вокруг обработчика. Сервер запускает shutdown-функции запроса, сбрасывает буферы вывода, закрывает сессию и заново заполняет суперглобальные переменные. Значения вне обработчика остаются в памяти. Rapira не запускает все деструкторы в конце запроса. PHP уничтожает объект после удаления последней ссылки на него.

## Один обработчик на воркер

`handle_request()` возвращает управление после каждого запроса. Скрипт воркера должен содержать цикл, который продолжает работу воркера.

Скрипт воркера выполняет один обработчик за раз. Второй последовательный цикл начнётся только после завершения первого. Первый цикл завершается, когда `handle_request()` возвращает `false`. В этот момент воркер уже останавливается. Распределяйте запросы внутри одного обработчика вместо использования нескольких циклов.

```php
while (\Rapira\handle_request($api)) {
}

// Code reaches this loop only during shutdown.
while (\Rapira\handle_request($web)) {
}
```

## Состояние между запросами

Объекты, созданные **вне** обработчика, существуют до перезапуска скрипта воркера. К ним относятся автозагрузчик, контейнер, маршруты, конфигурация, открытые соединения и кешированные данные. Rapira не создаёт их для каждого запроса.

Значения, созданные **внутри** обработчика, принадлежат одному запросу. PHP освобождает их после возврата обработчика и удаления последних ссылок.

Скрипт воркера определяет время жизни состояния. Размещайте состояние приложения перед циклом. Размещайте состояние запроса в обработчике или сбрасывайте его перед следующим запросом.

::: warning
Глобальное состояние также сохраняется между запросами. К нему относятся статические свойства, синглтоны, реестры и постоянные изменения `ini_set()`. php-fpm сбрасывает эти значения при завершении запроса. Воркер Rapira их не сбрасывает. Используйте [режим Classic](/ru/docs/classic), если приложение не может сбросить глобальное состояние. Режим Classic совместим с php-fpm. Выберите режим Worker после исправления глобального состояния.
:::

## Shutdown-функции

Shutdown-функция, зарегистрированная при инициализации, выполняется один раз при завершении цикла воркера. Она не выполняется после каждого запроса. Shutdown-функция, зарегистрированная обработчиком, выполняется один раз в конце этого запроса.

Уборку ресурсов, общих для всего процесса, регистрируйте при старте, а уборку того, что принадлежит одному запросу, - внутри обработчика.

```php
register_shutdown_function(static function (): void {
    // Runs once when the worker cycle ends.
});

$handler = static function (): void {
    register_shutdown_function(static function (): void {
        // Runs at the end of this request.
    });
};

while (\Rapira\handle_request($handler)) {
}
```

В конце цикла первыми отрабатывают стартовые регистрации, в порядке регистрации. Функция, зарегистрированная скриптом уже после цикла, выполняется после них.

Для объектов действует другое правило. Rapira не запускает все деструкторы в конце запроса. PHP уничтожает объект после удаления последней ссылки на него. Поэтому объект обработчика уничтожается после возврата обработчика. Глобальный объект, созданный при инициализации, остаётся между запросами. Его метод `__destruct()` выполняется один раз при завершении цикла.

::: question Почему shutdown-функция, зарегистрированная при старте, не выполняется в конце первого запроса?
PHP хранит shutdown-функции в состоянии запроса. При завершении запроса PHP вызывает функции и освобождает список. При первом вызове `handle_request()` Rapira удаляет и сохраняет стартовые регистрации. После этого каждый запрос содержит только свои регистрации. В конце цикла Rapira восстанавливает сохранённый список. Затем сервер добавляет регистрации, созданные после цикла. Финальное завершение сначала выполняет стартовые регистрации по порядку. Затем оно выполняет более поздние регистрации.
:::

## Только в режиме Worker

Функции `handle_request()` нужен резидентный цикл, а он есть только в режиме Worker. В режимах Classic и Dispatcher функция бросает `Rapira\Exception\NotInWorkerModeError`. Каждый класс, который бросает Rapira, реализует маркерный интерфейс `Rapira\Exception\RapiraThrowable`, поэтому одного `catch` хватает на все из них.

`Rapira\get_mode()` возвращает [режим](/ru/docs/execution-modes) текущего процесса как вариант перечисления `Rapira\Mode`. Скрипт, который работает больше чем в одном режиме, читает его до входа в цикл:

```php
if (\Rapira\get_mode() === \Rapira\Mode::Worker) {
    while (\Rapira\handle_request($handler)) {
    }
}
```

## Типичные проблемы

**Состояние сохраняется между запросами.** Проверьте состояние запроса, если приложение не работает только в режиме Worker. Примеры: растущий статический массив, объект запроса в синглтоне или старые данные пользователя в логгере. Сбрасывайте это состояние в начале или конце обработчика. Также сбрасывайте состояние запроса в библиотеках. `pool.max_requests` заменяет воркер после заданного числа запросов. Эта настройка ограничивает утечку памяти, но не исправляет её.

**Несобранные циклические ссылки.** Подсчёт ссылок PHP сразу освобождает большинство значений. Циклы освобождаются только при запуске сборщика циклов. Пример вызывает `gc_collect_cycles()` между запросами. Этот вызов не обязателен, но делает время сборки предсказуемым.

**Незавершённые запросы.** Воркер не может обрабатывать другой запрос во время выполнения текущего запроса. `pool.request_terminate_timeout_secs` ограничивает время одного запроса. Rapira завершает воркер, который превышает это значение. Этот ключ и `pool.max_requests` описаны в [Конфигурации](/ru/docs/configuration). Обработка завершения описана в разделе [Модель процессов](/ru/docs/process-model).

**Непойманное исключение затрагивает один запрос, а не воркер.** Rapira возвращает `500` для непойманного исключения обработчика, если обработчик ещё не отправил заголовок ответа. Rapira не может изменить статус после отправки заголовка ответа. Цикл продолжается, поэтому исключение не останавливает воркер. Фатальная ошибка завершает резидентный скрипт. Затем воркер снова запускает скрипт и инициализирует приложение.

**Работа после ответа.** `rapira_finish_request()` отправляет ответ до завершения обработчика. Например, после этого обработчик может записать событие аудита. Дополнительная информация находится на странице [HTTP](/ru/docs/http).

## Стаб-файлы для IDE

Rapira объявляет функции и классы PHP в стаб-файлах каталога `crates/php_sys`. API воркера находится в [`rapira.stub.php`](https://github.com/rapira-rs/rapira/blob/main/crates/php_sys/rapira.stub.php). Классы исключений находятся в [`rapira_exception.stub.php`](https://github.com/rapira-rs/rapira/blob/main/crates/php_sys/rapira_exception.stub.php). Эти файлы содержат основные объявления сигнатур, типов свойств и назначения классов. Они также служат стабами IDE. Добавьте их в проект для автодополнения API Rapira.
