# Режим воркера

В [классическом режиме](/ru/docs/classic) PHP ведёт себя ровно так, как привык: входной скрипт выполняется с нуля, запрос получает ответ, и всё, что скрипт успел построить, выбрасывается. Поднять современный фреймворк — автозагрузчик, контейнер, конфигурацию, маршруты, соединения с базой — стоит одинаково и на первом запросе, и на миллионном.

Режим воркера — это альтернатива. Процесс остаётся живым: скрипт один раз поднимает приложение и уходит в цикл, каждый виток которого просит у Rapira очередной запрос. За старт вы платите один раз, а каждый следующий запрос попадает в уже прогретое приложение. Взамен придётся думать о состоянии, потому что теперь оно живёт дольше запроса.

Это ступень **SAPI Worker** на лестнице режимов выполнения Rapira; вместе с Classic она готова уже сегодня. Про всю лестницу и про то, как понять, до какой ступени дотянется ваше приложение, рассказывают [Режимы выполнения](/ru/docs/execution-modes), а эта страница — руководство по той ступени, которой можно пользоваться прямо сейчас.

## Резидентный цикл

Скрипт воркера состоит из трёх частей: всё, что вы поднимаете в начале файла, обработчик, отвечающий на один запрос, и цикл, который крутит обработчик, пока сервер не остановится. Цикл написан на PHP — Rapira выдаёт вам объект-обработчик, а управляете им вы сами.

```php
<?php
// worker.php
require __DIR__ . '/vendor/autoload.php';

use Rapira\Plugin\Http\HttpHandlerConfig;
use function Rapira\create_plugin_handler;

$http = create_plugin_handler(new HttpHandlerConfig());
$app = new App(); // booted once, reused for every request

$handler = static function () use ($app): void {
    header('Content-Type: text/plain');
    http_response_code(200);
    echo $app->handle($_SERVER['REQUEST_URI']);
};

while ($http->handleRequest($handler)) {
    gc_collect_cycles();
}
```

Осталось направить на него сервер — и всё: режим воркера у `rapira serve` включён по умолчанию, а классический включается явно:

```bash
rapira serve app/worker.php
```

Остальные флаги собраны в разделе [Командная строка](/ru/docs/cli), а их аналоги для `rapira.toml` — в [Конфигурации](/ru/docs/configuration).

## Что делает `handleRequest()`

`handleRequest(callable $handler)` — это весь контракт целиком, и его стоит прочитать не спеша:

- **Блокируется** до тех пор, пока воркеру не достанется запрос. Пока воркер стоит на `handleRequest()`, процессор он не расходует, но продолжает держать в памяти свой интерпретатор и поднятое приложение.
- **Заполняет суперглобальные переменные** — `$_GET`, `$_POST`, `$_SERVER`, `$_COOKIE` и всё остальное семейство — данными пришедшего запроса, заново и до того, как выполнится ваш обработчик. Обычный PHP-код, который их читает, работает точно так же, как под php-fpm.
- **Вызывает ваш обработчик без единого аргумента.** Всё о запросе уже лежит в суперглобальных переменных, поэтому сигнатура колбэка — `function (): void`. Всё остальное, что ему нужно — контейнер, приложение, логгер, — захватывайте через `use`.
- **Ответом становится ваш вывод.** `echo`, `print`, `header()`, `http_response_code()`, `setcookie()` — обработчик формирует ответ ровно так же, как классический скрипт. Как связаны данные запроса и вывод ответа, разбирает раздел [HTTP](/ru/docs/http).
- **Возвращает `true`**, когда запрос закончен, то есть «продолжаем», и **`false`**, когда сервер останавливается. На этом и держится цикл: как только пришло `false`, выходите из него и дайте скрипту завершиться.

Получается, что запрос в режиме воркера — это один виток вашего цикла `while`. Rapira закрывает запрос вокруг обработчика: отрабатывают shutdown-функции и деструкторы, буферы вывода сбрасываются и обнуляются, сессия записывается и закрывается, а суперглобальные переменные наполняются заново к следующему витку. Всё, что скрипт держит за пределами обработчика, при этом остаётся нетронутым.

## Один обработчик — один воркер

`handleRequest()` возвращает управление после каждого запроса. Это не вызов «обслуживай вечно»: воркер живёт благодаря циклу вокруг него, и этот цикл пишете вы.

Отсюда следует то, на чём часто спотыкаются: скрипт воркера крутит ровно один обработчик за раз. Если написать два цикла подряд, до второго дело не дойдёт, пока не завершится первый, а первый завершится только тогда, когда `handleRequest()` вернёт `false`, то есть когда сервер уже останавливается. Разводить запросы по разным веткам кода должен сам обработчик, внутри себя, а не несколько циклов.

```php
while ($http->handleRequest($api)) {
}

// unreachable until shutdown
while ($http->handleRequest($web)) {
}
```

## Что живёт между запросами

Всё, что вы создаёте **вне** обработчика, живёт столько же, сколько процесс воркера: автозагрузчик, DI-контейнер, скомпилированные маршруты, конфигурация, открытые соединения с базой и кешем, прогретые кеши. В этом и весь смысл режима воркера — именно за это вы перестаёте платить на каждом запросе.

Всё, что вы создаёте **внутри** обработчика, — обычная работа на один запрос: она освобождается, когда обработчик возвращает управление и запрос разбирается.

Граница между этими двумя частями и есть то проектное решение, которое от вас требует режим воркера. Состояние, задуманное общим, поднимайте наверх; состояние одного запроса оставляйте в обработчике или сбрасывайте до прихода следующего.

::: warning
Общим становится и всё глобальное, планировали вы это или нет: статические свойства, синглтоны, реестры, которые библиотека лениво наполняет по ходу дела, `ini_set()`, который вы так и не отменили. Под php-fpm всё это жило ровно один запрос, потому что завершение запроса в PHP сбрасывало и статику, и глобальные переменные, и `ini_set()`. Воркер Rapira этот сброс между заданиями намеренно пропускает, так что теперь не сбрасывается ничего.
:::

## Выбор плагина

`create_plugin_handler()` принимает объект конфигурации, и плагин выбирается по *классу* этого объекта. `HttpHandlerConfig` говорит «этот воркер обслуживает HTTP» — и в ответ вы получаете `HttpHandler`.

Исключение `Rapira\RapiraException` она бросает в двух случаях: когда переданному классу конфигурации не соответствует ни один плагин и когда скрипт вообще запущен не в режиме воркера — в классическом режиме резидентного цикла нет, так что обработчику там осталось бы только сообщать об остановке.

Конфигурация ещё и описывает, к чему она относится: в `$http->config->info` лежит `Rapira\PluginInfo` с полями `name` и `description` (для HTTP-плагина это `http` и `HTTP request handler`):

```php
$http = create_plugin_handler(new HttpHandlerConfig());

echo $http->config->info->name;        // http
echo $http->config->info->description; // HTTP request handler
```

## Как следить за воркером через `getInfo()`

`$http->getInfo()` возвращает `Rapira\Plugin\Http\RuntimeInfo` — счётчики самого этого воркера, снятые в момент вызова:

| Поле       | Что это                                                                        |
| ---------- | ------------------------------------------------------------------------------ |
| `state`    | `starting`, `idle`, `active`, `draining` или `free` — см. ниже                  |
| `pid`      | Идентификатор процесса этого воркера                                            |
| `queued`   | Сколько запросов прямо сейчас ждёт в очереди этого воркера                      |
| `handled`  | Сколько запросов воркер довёл до конца                                          |
| `errors`   | Сколько из них закончились ошибкой                                              |
| `recycles` | Сколько раз воркеру пришлось пересобирать состояние после аварийного выхода PHP |
| `restarts` | Сколько раз пришлось пересоздавать сам PHP-поток воркера                        |

Пять состояний описывают, где воркер находится в своём жизненном цикле: **starting** — мастер-процесс его форкнул, а он ещё не отчитался; **idle** — стоит и ждёт запроса, считаясь свободным резервом; **active** — обрабатывает запрос; **draining** — решил завершиться (исчерпал квоту запросов или был помечен нездоровым) и в резерв больше не входит; **free** — за слотом вообще не закреплён воркер.

Обратите внимание: `queued` — это текущая глубина очереди, а не накопленный итог, и все счётчики относятся только к этому процессу. Они обнуляются при старте воркера, поэтому пришедший на замену воркер считает с нуля заново.

Напрашивается очевидное применение — маленький эндпоинт со статусом:

```php
$handler = static function () use ($http): void {
    $info = $http->getInfo();
    header('Content-Type: application/json');
    echo json_encode([
        'pid' => $info->pid,
        'state' => $info->state,
        'queued' => $info->queued,
        'handled' => $info->handled,
        'errors' => $info->errors,
    ]);
};
```

## Подводные камни

**Состояние протекает между запросами.** Это главная беда, и почти всегда именно из-за неё приложение ведёт себя странно в воркере, но не под php-fpm. Растущий статический массив, объект запроса, осевший в синглтоне, логгер, который держит контекст прошлого пользователя, — каждая такая мелочь проявляется только на втором запросе. Прибирайтесь явно, в начале или в конце обработчика, и сбрасывайте всё, что оставила после себя библиотека. Подстраховка тоже есть: `pool.max_requests` заставляет воркер завершиться после N запросов, чтобы мастер-процесс заменил его свежим. Это ограничивает ущерб от медленной утечки, но это страховка, а не лечение.

**Мусор, у которого нет хозяина.** Подсчёт ссылок в PHP освобождает почти всё сразу, но циклические ссылки достаются сборщику циклов и ждут его запуска. Вызов `gc_collect_cycles()` на каждом витке цикла — как в каноническом скрипте выше — собирает их в предсказуемый момент: между запросами, а не посреди одного из них.

**Запросы, которые никогда не кончаются.** Резидентный воркер готов вечно сидеть внутри зависшего запроса, и всё это время он не обслуживает никого. `pool.request_terminate_timeout_secs` задаёт предел по реальному времени на один запрос и убивает воркер, который в него не уложился. Оба ключа описаны в [Конфигурации](/ru/docs/configuration), а что делает мастер-процесс, когда воркер умирает, рассказывает [Модель процессов](/ru/docs/process-model).

**Непойманное исключение стоит запроса, а не воркера.** Непойманное исключение в обработчике попадает в счётчик `errors`, а клиент получает `500` — если, конечно, обработчик не успел зафиксировать статус до того, как бросил. В любом случае цикл продолжается: исключение не уносит воркер с собой, так что сбой, о котором вы читаете в логах, вовсе не обязательно что-то остановил. С фатальной ошибкой иначе: она сворачивает резидентный скрипт, поэтому воркер выполняет его заново с самого начала и снова поднимает приложение. Именно это и считает счётчик `recycles`.

**Работа после ответа.** Если нужно отдать ответ и продолжить работу — разгрести очередь, записать событие в аудит, — ровно это и делает `rapira_finish_request()`. Она описана на странице [HTTP](/ru/docs/http).

## Стаб-файл для IDE

Все классы и функции, которые Rapira отдаёт в PHP, объявлены в [`crates/php_sys/rapira.stub.php`](https://github.com/rapira-rs/rapira/blob/main/crates/php_sys/rapira.stub.php). Это авторитетное описание API — сигнатуры, типы свойств, назначение каждого класса, — и одновременно стаб для IDE: положите его в проект, и редактор начнёт подсказывать `create_plugin_handler()`, `handleRequest()` и всё остальное вместо того, чтобы подчёркивать их как неизвестные.

::: question Нужен ли особый фреймворк, чтобы работать в режиме воркера?
Нет — нужно приложение, которое переживёт единственный запуск и множество запросов после него. Большинство современных фреймворков на это способны, а для тех, о которых мы уже написали, детали собраны в [руководствах по фреймворкам](/ru/docs/frameworks/).
:::

::: question Обязателен ли `gc_collect_cycles()` в цикле?
Не обязателен, но это хорошее значение по умолчанию. Без него циклические ссылки копятся, пока сборщик PHP не решит запуститься сам — возможно, прямо посреди чьего-то запроса. Вызов между запросами удерживает эту работу в предсказуемой точке.
:::

::: question В приложении есть глобальное состояние, от которого не избавиться. Rapira всё равно подойдёт?
Да: запускайте его в [классическом режиме](/ru/docs/classic). Выигрыш от прогретого старта вы потеряете, зато получите замену php-fpm без единой правки, а перейти на воркер сможете позже, когда состояние будет распутано.
:::
